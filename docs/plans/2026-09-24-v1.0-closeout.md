# Career OS v1.0 收口计划

日期：2026-09-24
状态：第一周工程项已完成并通过离线验证（见第 8 节）；第二周需要联网环境与模型凭据

## 0. 一句话目标

v1.0 不以“28 个 source COMPLETE”为目标，而是完成**一个真实用户任务闭环**：

> 候选人问“我现在最该看哪些岗位”，系统从官方公告出发，给出至少 10 个经人工确认进入可信池的岗位，
> 每个岗位附逐条资格结论和可点开的官方原文片段；Agent 的每一步工具调用和证据来源都落库、可回放。

P1/P2 数据完整性继续迭代，但任何一项都不得阻塞 v1.0。

## 2. 删除 / 延期

### 冻结（v1.0 期间不做，任何一项都不得阻塞 v1.0）

- **新增 source 接入**。已登记的来源保持现状，只维护下面的 P0 集合；不再为新区县、新医院写迁移。
- 六级来源完整性审计（`SourceCompletionAudit` 的检查项继续保持 `UNKNOWN`）。
- 生命周期公告关联的扩展、跨年岗位族与再现预测的扩展。
- 投递跟踪、提醒推送、笔试进度（原 P2）。
- chance／growth／future／preparation_cost 评分维度，`MUST_TRACK` 等策略等级。
- 权威专业目录映射、政策源（原 P1）；现有“专业名称精确匹配 + 门类判待确认”的保守规则不变。
- 多用户授权；继续按单人可信部署。
- Agent 写入类工具；v1.0 的 Agent 仍然只读。
- G1–G7 类边界反例的继续打磨（`docs/audits/2026-09-1x`），除非在真实运行里复现。

### 收起 / 删除

- 前端“只读工具编排”调试面板不再作为用户入口：v1.0 合并为一个输入框，轨迹移到运行台账页（第二周）。
- `agent-app`、`crawler-service` 两个已隔离的实验模块：v1.0 发布前删除（本轮不动，避免混进无关改动）。

## 4. Agent 最小闭环设计

```
官方公告/附件 ─采集→ 解析 → 字段证据 → 自动准入（数据质量 VERIFIED？）
                                              │
                                  人工范围确认（新增，REVIEWER）
                                  纳入 / 排除，绑定内容指纹，追加式台账
                                              │
                                              ▼
                                    可信池（VERIFIED + INCLUDED）
                                              │
用户任务 → 规划器（真实 LLM）→ 只读工具 ──────┘
             ▲      │           search_jobs / job_facts / pending_confirmations / watchlist
             │      │           观测带证据：官方链接、字段原文片段、片段 ID（新增）
             │      ▼
             │   执行器校验：模板封闭、依据点名、预算、步数（已有）
             │      │
             └──────┤
                    ▼
        响应（岗位与证据由程序渲染） + 运行台账（新增）
        agent_run / agent_run_step / agent_model_turn
                    │
                    ▼
        案例报告（新增脚本）：每个推荐 = 岗位 + 逐条资格 + 官方原文 + Agent 调用链
```

五个新增部件，都不改变“模型只选工具、结论由程序算”的边界：

1. **人工范围确认**（G1）。只对自动准入已判数据质量为 `VERIFIED`、用工身份已知、未被规则排除的岗位开放；
   请求必须带上审核时看到的内容指纹，岗位内容变了就 409。决定写入追加式台账，岗位内容再变化时，
   已有的数据库触发器会照旧撤销准入。这一步是人做判断，不是降低门槛。
2. **证据进观测**（G4）。`job_facts` 返回逐条规则（含引用的片段 ID）和每个字段的官方链接、定位、原文片段；
   `search_jobs` 与 `job_facts` 每行带岗位所在的官方文件（有岗位表附件时是附件，否则是公告页）。
3. **运行台账**（G3、需求 5）。每次运行记录：规划器身份（模型名 + 端点主机，或 recorded／scripted）、
   问题、结局、渲染出的回答或追问、被拒原因；每一步记录工具、参数、理由、是否被接受、拒绝原因、
   结果摘要、预算和**证据引用**；模型规划器的每一轮记录原始输出和提示哈希，可据此回放。
5. **准入重算**（G6b）。复核人可按当前规则重新评估全部在招岗位的自动准入，人工决定保留，分批提交。
4. **模型名下传**（G2）。`career-os.agent.llm.model`（默认取 `CAREER_OS_AI_MODEL`）与可选的
   `career-os.agent.llm.temperature` 写进规划器的默认选项；抽取器同样使用自己配置的模型名。

## 6. v1.0 完成定义（DoD）

1. 可信池 ≥ 10 个岗位（`VERIFIED + INCLUDED`、用工身份已知），来自 ≥ 2 个 P0 来源。
2. ≥ 10 个推荐案例：每个含岗位与单位、分层、逐条资格结论、至少一条官方原文片段和公告链接。
3. 3 个真实 Agent 场景由真实模型跑通，作为产品验收案例（2026-09-24 调整，取代“10 次运行”）：
   **岗位发现**（search_jobs 查到可信岗位）、**资格解释**（job_facts 给出逐条资格与字段原文）、
   **岗位比较与决策辅助**（job_facts 读两个不同岗位，按比较模板收尾）。每个案例记录用户输入、
   工具调用链、使用的数据、证据来源和最终输出；叙述被执行器拒绝就如实记为未通过，不删样本、不挑重跑结果。
4. CI 全绿，包含闭环端到端测试；跳过门禁不新增例外。
5. README 与实测一致。

## 7. 本环境的限制（如实记录）

本计划写成时所在的云端开发环境，出网策略拒绝了全部官方招聘站点（38 个主机里 36 个超时、2 个 403）
和全部模型端点，也没有模型凭据。因此第一周的交付全部离线可验证，第二周的第 1、3、4 步必须在能联网、
有凭据的环境里执行。不在没有真实运行的情况下声称“已接通真实模型”或“已有真实案例”。

## 9. 第二轮（2026-09-24，P0 调整后）

P0 调整为：用现有 P0 来源形成真实可信池（≥ 10）、联网接通模型、跑通 3 个真实 Agent 场景。
暂缓项不变（更多来源、六级覆盖、投递管理、多用户、高级评分）。

| 部件 | 落点 | 验证 |
|---|---|---|
| 比较场景的收尾 | 新模板 `JOB_COMPARISON`，适用条件是依据里至少有两个**不同**岗位的 `job_facts`；同一岗位读两遍、或只读一个都被拒 | 执行器测试；全部模板的叙述校验 |
| 可并排的事实 | 查询与详情每行带建议状态、适配指数、稳定指数、官方文件；Agent 面板并排显示 | 工具测试、前端测试 |
| 场景验收 | `scripts/v1_closed_loop.py` 改为 3 个场景（后两个续接发现场景的会话，“第一个/第二个”指用户看到的那份列表；模型追问时自动答一次并记两轮），逐场景记录输入、调用链、使用的数据、按岗位分组的证据、最终输出与被拒原因 | Python 24 |
| 中间层评估 | [Raw → AI Candidate → Trusted](../superpowers/specs/2026-09-24-ai-candidate-admission-layer-design.md)：值得加，但 AI 只提议“范围”；v1.0 不实施，V90 台账就是将来的标注集 | —— |

彩排（合成数据 + 录制的模型输出，经 `ModelPlanner` 解析与执行器校验；**不是**验收案例）：
三个场景除“真实模型规划”一项外全部检查通过——发现场景查到 5 个可信岗位并按列表模板收尾；
资格解释读到 9 条规则与字段原文；比较场景按会话里的“第一个、第二个”读了两个不同岗位，用比较模板收尾。
第一次彩排因为容器语言环境把命令行里的中文解码坏了，“杭州”变成乱码、查询为零；那一次执行器正确拒绝了
“列出岗位”的收尾，后两个场景也如实报告“没有上一轮的列表”——没有替零结果编出一份列表。

仍然阻塞：本环境对全部官方站点和模型端点的出网都被拒，也没有模型凭据。
第 5 节第二周的 1、3、4 步必须在联网、有凭据的环境里执行。
