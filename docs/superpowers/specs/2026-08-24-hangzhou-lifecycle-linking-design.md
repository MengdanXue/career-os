# 杭州招聘生命周期采集与关联设计

## 目标

Career OS 不再只采集首发招聘公告。对杭州官方来源中出现的资格复审、成绩、面试、体检、考察、公示和聘用公告，系统应保存官方证据，并在证据足以唯一定位时关联回原招聘事件。无法唯一关联的公告必须保留为待关联或歧义，不能丢弃，也不能猜测。

## 范围

本切片先覆盖已接入且能提供同栏目历史列表的杭州来源，首个真实验收源为西湖区政府招聘栏目。生命周期阶段包括 `QUALIFICATION_REVIEW`、`SCORE_RESULT`、`INTERVIEW`、`PHYSICAL_EXAM`、`INVESTIGATION`、`PUBLICATION` 和 `APPOINTMENT`。一个公告可命中多个阶段，例如“体检、考察对象名单”。

不在本切片中处理报名人的个人成绩，不抓取需要登录的系统，不根据姓名或身份证匹配个人，不把后续公告解析成新的招聘事件。

## 数据模型

新增 `recruitment_lifecycle_document`。每个“官方公告 URL + 阶段”保存一行，包含标题、年份、发布时间、证据、匹配状态、匹配到的招聘事件和匹配依据。匹配状态只有：

- `MATCHED`：恰好一个招聘事件满足确定性规则；
- `UNMATCHED`：没有达到阈值的候选；
- `AMBIGUOUS`：有多个同等可信候选。

URL 与阶段唯一，重复采集执行 upsert，从而支持增量运行而不重复通知。

## 分类与关联

标题分类采用确定性关键词，允许一个标题返回多个阶段。阶段词本身不用于招聘批次身份。关联时先截取生命周期词之前的招聘批次主干，删除“关于、公布、通知、公告”等噪声并规范标点；候选招聘事件采用相同规范化。只有同招聘年份、包含招聘语义、主干完全相等，或者较短主干长度至少 12 且双方包含、长度比不低于 0.75 时才成为候选。

恰好一个候选才关联；两个及以上候选一律记为 `AMBIGUOUS`。关联成功后只把对应流程阶段设为 `CONFIRMED`，并在详情字段保存后续公告标题和官方 URL。原事件的岗位、用工性质和资格条件不因生命周期公告改变。

## 采集数据流

官方列表发现器允许生命周期标题进入候选集。HTML/PDF 仍先进入现有证据提取链路；处理器在标题被分类为生命周期公告时调用专用服务并停止普通招聘公告 upsert，防止生成没有岗位的伪招聘事件。普通招聘公告和 Excel 岗位导入保持原逻辑。

## 展示与审计

来源 API 增加生命周期公告总数、已关联数、待关联数和歧义数。岗位/招聘事件现有流程详情通过已更新的阶段状态看到关联结果；后续 UI 可下钻到生命周期公告证据。未匹配与歧义不是采集失败，也不能提升来源为完整接入。

## 验收

- 分类器正确识别单阶段和多阶段标题，不把普通招聘公告识别为生命周期公告；
- 唯一批次匹配后更新对应招聘事件，重复处理不新增重复行；
- 无候选和多候选分别保持 `UNMATCHED`、`AMBIGUOUS`；
- 西湖区配置不再排除生命周期标题；
- 来源 API 返回四个生命周期计数；
- 全量 Java 与前端测试通过，真实来源运行不产生新的伪招聘事件。
