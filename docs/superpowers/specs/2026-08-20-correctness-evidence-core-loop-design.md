# Career OS 正确性与证据核心闭环修正设计

**状态：** 待用户最终审阅

**日期：** 2026-08-20

**依据：** `docs/CAREER_OS_MASTER_SPEC.md`、`docs/product-requirements.md`

**目标：** 将当前“可采集、可展示”的工程底座修正为真正满足杭州/浙江稳定技术岗位决策需求的业务 MVP。

## 1. 结论与范围

当前版本不能继续以“业务 MVP 已完成”验收。它已具备可复用的采集、附件解析、内容指纹、增量差异、审核队列、数据库和网页底座，但尚未形成可信职业决策闭环。

本子项目只完成以下闭环：

```text
真实候选人事实确认
  → 原始岗位保留与目标岗位筛选
  → 用工身份有证据判定
  → 岗位与政策字段有证据规范化
  → 硬资格逐条判断
  → Fit / Stability 分维度解释
  → T1 / T2 / T3 / 排除正确分池
  → Eligibility Explanation Agent 回答“能不能报、为什么、还要确认什么”
  → 形成可信 Top 20
```

本子项目不实现跨年度概率模型、简历生成、面试题库、自动投递或复杂多 Agent 自治。历史关联、2027 关注日历、材料和申请执行在该闭环通过验收后分别进入后续子项目。

## 2. 已核实的当前问题

2026-08-20 对本地真实数据库的核查结果：

- 共有 2291 个岗位，但 2291 个岗位的 `employment_type` 全部为 `UNKNOWN`；
- 2042 个岗位被归为 `OTHER`，当前列表混入教师、行政及明显非目标岗位；
- 只有 312 个岗位带专业和年龄字段，工作经历、职称要求均未被结构化；
- 岗位级 `evidence_ids` 全部为空；
- 当前候选人仍叫 `MVP Seed Candidate`，毕业时间、经历、技能、研究方向和单位偏好未完成；
- 最新决策中 2068 个岗位以 `UNCERTAIN` 进入 T3，平均证据覆盖率约 8.6%；
- 现有 Agent 只用关键词从问题中识别 T1/T2/T3、地点和岗位族，然后调用排名接口，不具备政策、证据和资格工具编排能力。

因此当前的 2291 条数据只能视为原始采集资产，不能视为 2291 个可决策机会。

## 3. 三种处理方式与决策

### 方案 A：正确性与证据优先（采用）

保留原始采集数据，但建立正式数据准入门槛。只有目标岗位分类、用工身份、核心资格字段和证据链达到要求的岗位才能进入机会池。先完成 30–50 个 Golden Jobs，再扩大覆盖。

优点是符合主规范 `Correctness > Evidence > Eligibility > Decision Quality > Automation > Number of Crawled Jobs`，并能让 Agent 的答案真正可信。代价是短期内机会池数量会从 2082 大幅下降。

### 方案 B：先扩来源和岗位数量（不采用）

继续接更多网站可以迅速增加原始记录，但会进一步放大 `UNKNOWN`、无证据和无关岗位问题，无法改善用户决策。

### 方案 C：先强化聊天 Agent（不采用）

在当前低质量数据上增加模型、RAG 或复杂对话只会让错误结论表达得更自然，违反硬资格和用工性质不得猜测的原则。

## 4. 数据分层与正式准入门槛

### 4.1 原始库与机会库分离

所有已采集岗位继续保留，不清库、不物理删除。岗位使用以下数据状态：

- `RAW`：仅完成采集；
- `PARSED`：已解析出候选字段；
- `NORMALIZED`：单位、事件、岗位和字段已规范化；
- `REVIEW_REQUIRED`：重要事实缺失、冲突或低置信度；
- `VERIFIED`：通过自动规则和必要的人工复核；
- `REJECTED`：无效记录或确认不属于招聘岗位。

“更新岗位库”可以展示所有状态。“机会池”和 Agent 排名默认只能读取 `VERIFIED` 且属于目标范围的岗位。

### 4.2 目标岗位分类

每个岗位产生独立的目标范围结论：

- `INCLUDED`：计算机、软件、数据、AI 应用、信息化、数字政府、医院/高校信息中心、科研工程技术等目标岗位；
- `EXCLUDED`：教师、博士后、纯行政、党建、销售、实习、明显非技术岗位等；
- `NEEDS_REVIEW`：标题不足以判断，需要结合职责、专业和单位部门。

排除结论保存原因码和证据，原始岗位仍保留。筛选不能只依赖标题关键词；确定性词表负责明确包含/排除，含糊职责由结构化抽取提出建议并进入复核。

### 4.3 用工身份准入

用工身份使用主规范完整枚举：

- `PUBLIC_INSTITUTION_ESTABLISHMENT`
- `PUBLIC_INSTITUTION_FORMAL`
- `QUOTA_EMPLOYMENT`
- `UNIVERSITY_FORMAL`
- `RESEARCH_INSTITUTE_FORMAL`
- `SOE_FORMAL`
- `GOVERNMENT_PLATFORM_FORMAL`
- `CONTRACT`
- `LABOR_DISPATCH`
- `PROJECT_BASED`
- `UNKNOWN`

用工身份作为独立 assessment 保存：结论、事实状态、证据、置信度、规则/模型版本和人工复核状态。单位类型不能替代用工身份；没有公告原文或官方说明时只能是 `UNKNOWN`。

T1/T2/T3 只能由已确认的用工身份和岗位范围产生：

- T1：明确事业编制；
- T2：已确认的高校/科研院所正式、员额或稳定公益合同岗位；
- T3：已确认的国企正式或政府数字平台正式岗位；
- `UNKNOWN` 不进入 T3，进入“待确认”。

## 5. 候选人事实模型

现有候选人 ID 和历史决策保留，但 Seed Profile 不再直接作为有效决策资料。

候选人表继续保存强类型字段，并为每个会影响资格的字段记录确认状态：

- `CONFIRMED`：用户确认，可用于硬资格；
- `PENDING`：已有候选值但未确认；
- `UNKNOWN`：尚无事实；
- `NOT_APPLICABLE`：该用户不适用。

第一轮必须覆盖：

- 完整出生日期；
- 学历、学位、境内/境外类型、专业原文；
- 毕业日期；
- 留服认证状态、认证专业名称和预计/实际完成日期；
- 工作经历年限及关键经历；
- 劳动合同、社保、档案和未落实工作单位状态；
- 中级职称全称、取得方式和日期；
- Java/企业系统/数据库/信息化技能；
- AI/GNN/机器学习研究事实；
- 目标岗位族、单位类型、地区和排除项。

任何未确认事实不得被资格引擎当作满足。界面必须明确显示“这会影响哪些资格判断”。

## 6. 岗位、政策与证据

### 6.1 岗位字段

在现有岗位基础上补齐本闭环需要的字段：

- 学位、专业原文和规范化专业；
- 年龄原文和基准日期；
- 应届要求；
- 境外学历、留服和专业认定规则；
- 未落实工作单位、社保和档案规则；
- 工作经历原文；
- 职称、政治面貌和其他组合条件；
- 笔试、笔试科目、专业测试和面试形式；
- 报名开始、截止时间；
- 原始要求文本和附件定位。

### 6.2 证据绑定

不再只在岗位上保存一个证据 ID 数组。新增字段级证据绑定：

```text
entity_type + entity_id + field_name
  → evidence_id
  → source URL / artifact hash / 页码或表格行 / 原文片段
```

年龄、学历、专业、应届、留服、社保、经历、职称、用工身份、报名截止等限制性字段必须有证据或显式为 `UNKNOWN`。模型提取的事实必须通过 JSON Schema、枚举规范化和证据定位校验后才能成为候选事实。

### 6.3 政策规则

岗位公告与上位政策分开保存。第一轮只实现影响当前候选人的政策类型：年龄、应届、境外学历、留服、专业认定、社保/未就业、工作经历和职称。

政策缺失或冲突时，资格结果保持 `UNCERTAIN`，并用细分原因表达：

- `CONDITIONAL`：取决于未来事件，例如留服完成日期；
- `NEEDS_CONFIRMATION`：需要用户或招录单位确认；
- `CONFLICTING_EVIDENCE`：官方材料之间存在冲突。

这样保留主规范的总体资格枚举，同时满足产品对不确定原因的精确表达。

## 7. 资格、评分与推荐

### 7.1 硬资格

Java 规则逐条计算年龄、学历、学位、专业、应届、境外学历/留服、社保/未就业、工作经历、职称和其他明确条件。每条结果必须包含：

- 状态；
- 候选人事实；
- 岗位或政策要求；
- 计算过程；
- 证据；
- 阻断原因或不确定原因。

任一明确不满足即为 `INELIGIBLE`。存在未确认硬条件时不能输出“可报”。

### 7.2 多维分析

本闭环保留 `Fit` 和 `Stability`，但没有证据的维度显示“待核实”，不能用 0 分伪装成负面事实。`Chance`、`Growth` 和 `Future` 仅在数据模型中预留，不在缺少历史和竞争数据时生成伪分数。

排名顺序是：资格 Gate → T1/T2/T3 → 证据完整度 → Fit → Stability。只有 `ELIGIBLE`，以及用户明确确认可接受条件后的特定 `UNCERTAIN` 岗位，才能进入“建议行动”。

### 7.3 Top 20

Top 20 必须是通过正式准入门槛的目标岗位，并逐条解释：

- 为什么属于目标技术岗位；
- 用工身份及证据；
- 能否报名；
- 匹配优势和短板；
- 稳定性已知事实和未知事实；
- 截止时间；
- 下一步动作。

如果不足 20 个，系统应诚实显示实际数量和缺口，不能用未知岗位补满。

## 8. MVP Agent 设计

当前关键词路由不再称为完整 Career OS Agent。本闭环按主规范只交付两个领域 Agent：

### 8.1 Recruitment Extraction Agent

输入公告正文和附件解析结果，调用确定性文档工具，输出严格 Typed DTO：岗位候选字段、字段证据、未知项和复核原因。它不能直接把岗位晋升为 `VERIFIED`，也不能推测用工身份。

### 8.2 Eligibility Explanation Agent

回答“我能不能报这个岗位、为什么、还缺什么”。Agent Orchestrator 只能调用以下只读工具：

1. `load_confirmed_candidate_facts`
2. `load_verified_job_facts`
3. `load_employment_identity_evidence`
4. `load_applicable_policy_rules`
5. `evaluate_eligibility`
6. `explain_eligibility`

最终资格状态完全来自 Java 规则工具。模型只负责理解用户指向的岗位、组织证据和表达答案；模型不可修改规则结果。每次 Agent 运行记录模型、提示词版本、工具调用、耗时、token、校验错误和回退状态。

没有模型配置时，同一工具链仍返回结构化确定性答案；这叫“离线解释模式”，界面不把它包装成模型推理。

## 9. 用户界面修正

### 我的资料

从简单资料表改为“已确认事实 / 待确认事实 / 对资格的影响”。Seed 名称不得继续显示为真实用户姓名。

### 更新岗位库

展示原始采集、解析、复核和正式入库数量。2291 条原始岗位保留在这里，不再等同于机会数量。

### 待复核

优先处理目标岗位范围、用工身份和硬资格字段。复核界面并排显示原文证据与候选结构化值。

### 机会池

默认展示“可行动”和“待确认”，再按 T1/T2/T3 分池。只读取正式准入岗位；无可信岗位时明确说明缺少哪一类证据。教师、行政等默认排除项不再污染目标机会列表。

### 岗位档案

先展示“能不能报”，再展示用工身份、目标岗位理由、Fit、Stability、证据和下一步。每项 UNKNOWN 都显示待确认内容及确认路径。

### Agent

第一版聚焦单岗位资格问答和 Top 20 解释，不承诺政策监控、预测、简历或面试能力。回答同时返回结构化资格维度和证据链接，不能只显示一段自然语言。

## 10. 迁移与兼容策略

- 不删除当前岗位、采集文档、附件、决策快照和用户操作；
- 新字段以迁移方式添加，现有岗位初始数据状态设为 `RAW` 或 `REVIEW_REQUIRED`；
- 旧 `ESTABLISHMENT` 等枚举映射到主规范的新枚举，无法确定的全部映射为 `UNKNOWN`；
- 旧决策保留为历史记录，但从新机会池查询中排除，并标记 evaluator 版本；
- 新决策只针对通过准入门槛的岗位计算，避免每次页面打开重算 2291 条低质量记录；
- 所有晋升、复核和重新评估操作必须幂等，可按规则/模型/内容版本重放。

## 11. Golden Dataset 与质量门槛

第一批人工校验 30–50 个 Golden Jobs，来源至少覆盖：

- 2026 杭州市市属事业单位招聘岗位表；
- 2026 高层次和特殊专业技术岗位表；
- 至少一份 2025 杭州历史公告；
- 至少一个医院信息中心岗位；
- 至少一个高校信息化岗位；
- 至少一个政府/事业单位信息中心或数据岗位；
- 至少一个国企或政府平台正式技术岗位；
- 明确的教师、博士限定、行政、派遣和项目制反例。

Golden Jobs 对招聘人数、年龄、学历、学位、专业、应届、社保/未就业、经历、职称、考试形式、用工身份、目标岗位分类和证据定位给出人工期望。

正式准入要求：

- 关键硬条件 Precision ≥ 95%；
- 用工身份无证据时 UNKNOWN 的正确率 100%；
- 同批数据重复运行不产生重复岗位或重复变更；
- 所有限制性结论具有可定位证据；
- 所有自动排除保留原始记录和原因；
- Golden Jobs 的资格边界测试全部通过。

## 12. 错误处理与人工边界

解析失败、证据缺失、政策冲突、专业等同性、境外学历口径和组合资格条件不会被吞掉或自动猜测，而是进入带原因码的 Review Queue。

人工操作保持 `CONFIRM`、`CORRECT`、`REJECT`、`NEED_MORE_EVIDENCE`。修正必须创建可审计版本，不能覆盖原始证据。外部网站失败只影响对应来源，不得清空已有正式岗位或改变既有资格结论。

## 13. 测试策略

实现继续遵循测试先行：

- 领域测试：目标岗位分类、用工身份、候选人确认状态、硬资格边界；
- Golden Tests：30–50 个真实岗位的预期结构与资格结果；
- 解析测试：真实 XLS/XLSX、HTML、PDF 的字段与证据定位；
- 持久化测试：数据状态、字段证据、版本、幂等和旧数据迁移；
- Agent 测试：Typed DTO、工具调用边界、模型失败回退、禁止覆盖硬规则；
- API/UI 测试：原始库与机会池隔离、待确认状态、Top 20 和证据展示；
- 浏览器验收：用户完善真实资料 → 复核岗位 → 查看可报结论 → 询问 Agent → 加入关注。

## 14. 本子项目验收标准

只有同时满足以下条件才可称为业务 MVP 核心闭环完成：

1. 当前 2291 条原始记录不再作为 2082 个 T3 机会展示；
2. 一个真实候选人画像完成资格相关事实确认，未知项保持未知；
3. 30–50 个 Golden Jobs 经真实官方材料校验；
4. 目标岗位、默认排除岗位和待复核岗位正确分流；
5. 事业编、正式岗、员额、合同、派遣、项目制和未知不会混淆；
6. 年龄、学历、学位、专业、应届、留服、社保、经历和职称逐条判断；
7. 每个硬资格和用工身份结论可定位到官方证据；
8. T1/T2/T3 不接收用工身份 UNKNOWN 的岗位；
9. 能输出不凑数的可信 Top 20，并解释资格、匹配、稳定和下一步；
10. Recruitment Extraction Agent 和 Eligibility Explanation Agent 使用 Typed DTO，且不能覆盖确定性规则；
11. 全量测试、迁移测试和真实浏览器核心流程通过；
12. README 和状态文档明确区分“工程底座完成”与“业务 MVP 已验收”。

## 15. 后续子项目

核心闭环验收后再依次推进：

1. 2025–2026 历史关联、岗位族和单位 Watchlist；
2. 2027 关注日历、重复招聘信号与有依据的 Future Score；
3. Opportunity/Application 状态、截止提醒和材料元数据；
4. Resume Strategy Agent；
5. Interview Agent 与失败复盘；
6. 来源扩面到杭州各区、高校、医院、科研院所和国企。

这些能力不得反向降低本设计规定的证据和资格准入门槛。
