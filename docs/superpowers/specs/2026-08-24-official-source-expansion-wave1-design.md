# Career OS 第一批官方数据源扩展设计

**日期：** 2026-08-24

**状态：** 对话方案已确认，待书面规格复核

**范围：** 杭州电子科技大学、浙江工商大学、杭州市第一人民医院，补采 2024—2026 年招聘数据并接入每日增量采集

## 1. 背景与结论

Career OS 当前不是“岗位数量太少”这么简单，而是目标市场覆盖失衡：浙江省人社厅和杭州市人社局两个综合来源已形成正式采集，高校和医院路线主要依赖综合公告中的零散样本。目标来源目录虽登记 20 个官方来源，但实际运行的 `recruitment_source` 只有 2 个，浙江工商大学仅有目录配置和部分验证，不能视为已接入。

本期采用“价值优先、分批适配”的扩源方案。第一批验证三个与用户目标最相关的官方来源：

1. 杭州电子科技大学人事招聘官网；
2. 浙江工商大学人才招聘官网；
3. 杭州市第一人民医院官方招聘证据入口。

高校来源复用静态列表、公告正文和附件下载链路。医院来源采用安全双轨：2024 年采集旧 HTTPS 招聘系统中的历史公告；2025—2026 年采集医院主站、杭州卫健委、人社部门等 HTTPS 官方公告。医院 2025 年启用的新报名系统目前只公开 HTTP 地址，系统仅保留其报名链接，不自动抓取或调用。

三个来源都必须完成 2024—2026 年真实回采、岗位解析、证据入库和增量复跑后，才能标记为 `CONNECTED`。HDU 具备成为完整来源的确定性条件；ZJGSU 当前列表以外部微信公众号和高层次人才内容为主，市一医院又存在新旧系统迁移，两者都可能在本期结束时保持 `PARTIAL`。本期目标不是把目录数字从 20 改大，而是让每个来源状态与证据一致，并显著改善高校/医院信息化岗位的历史样本与考试流程证据。

## 2. 用户目标

本期直接服务于以下职业决策问题：

- 2027 届境外计算机硕士在杭州高校、医院是否存在信息化、软件、数据、网络安全或信息中心岗位；
- 这些岗位通常在什么月份发布、报名和考试；
- 学历、专业、年龄、应届身份、留服认证和工作经历如何要求；
- 是否笔试、专业测试或面试，考试内容和流程证据来自哪里；
- 历史岗位与当前有效机会如何区分；
- 每天复跑时只推送新增、变更和下线，不重复推送同一岗位。

## 3. 本期目标与非目标

### 3.1 目标

1. 建立可验证的来源接入生命周期，禁止配置即完成；
2. 接入 HDU、ZJGSU 和杭州市第一人民医院三种实际入口；
3. 回采每个来源 2024、2025、2026 三个自然年度的可访问官方数据；
4. 保存公告正文、附件、岗位表、流程通知和官方链接；
5. 复用稳定公告键、稳定岗位键和内容指纹，生成新增、变更、下线差异；
6. 保存附件行级解析失败，允许其余正确行继续入库；
7. 将来源年度覆盖事实反馈给规划和覆盖 API；
8. 用用户真实画像重新计算高校/医院路线，不用假数据填补样本。

### 3.2 非目标

- 本期不接入全部 20 个目录来源；
- 不绕过登录、验证码、访问频率限制或网站安全措施；
- 不自动报名、投递或向外部机构发送信息；
- 不以第三方招聘站内容替代官方证据；
- 不自动抓取市一医院仅提供 HTTP 的新报名系统；
- 不用浏览器自动化处理已有稳定 HTTPS/JSON 接口；
- 不因单次抓取成功就宣称来源完整；
- 不把无法访问的历史页面推断为没有招聘。

## 4. 方案取舍

### 4.1 采用：来源类型适配器 + 统一采集管线

不同官网只负责“发现官方工件”，后续下载、解析、规范化、指纹、差异和入库继续走现有统一管线。高校使用静态 HTML 发现器的站点配置；医院使用“官方证据入口集合”，将旧 HTTPS 招聘页与 2025—2026 年医院、卫健委、人社等 HTTPS 公告汇入同一来源身份。该方案能复用现有能力，又不会为了访问仅 HTTP 的报名系统降低全局安全边界。

### 4.2 不采用：为每个来源复制一套完整爬虫

复制式爬虫上线快，但会重复实现附件下载、幂等、错误记录和数据融合，后续每个来源的维护方式都不同。来源适配器应只处理入口差异。

### 4.3 不采用：统一 Playwright 浏览器抓取

浏览器适合真实依赖脚本渲染、且没有稳定 HTTPS 读取接口的页面。本批高校和医院证据入口优先使用 HTTPS/HTML，以降低运行成本和不确定性。只有后续确认新报名系统提供可信 HTTPS 只读接口时，才单独设计 API 或浏览器适配器，不能在本期静默放宽到 HTTP 抓取。

## 5. 总体架构

```text
OfficialSourceCatalog
        |
        v
SourceContractVerifier -----> Source onboarding state
        |
        v
OfficialArtifactDiscoverer
  |-- StaticHtmlDiscoverer (HDU / ZJGSU)
  `-- HospitalOfficialEvidenceDiscoverer (old HTTPS + official HTTPS notices)
        |
        v
ArtifactDownloader -> Document Processor -> Recruitment Event / Job
        |                    |
        |                    `-> Row-level import failures
        v
Stable URI + SHA-256 fingerprint
        |
        v
Incremental diff: ADDED / UPDATED / UNCHANGED / OFFLINE
        |
        v
Coverage ledger -> TargetSourceCatalog -> Planning/API/UI
```

边界要求：

- `OfficialArtifactDiscoverer` 只输出官方工件描述，不解析岗位语义；
- 下载器只获取并校验内容，不决定岗位资格；
- 文档处理器负责将正文或附件转为事件、岗位和流程事实；
- 增量引擎只根据稳定键和指纹判断差异；
- 覆盖账本只记录实际运行证据，不根据 YAML 的 `enabled` 推断完成；
- 规划层只消费已入库的官方事实和覆盖状态。

## 6. 来源接入生命周期

来源状态必须由可审计证据驱动。目录现有 `CONNECTED`、`PARTIAL`、`FAILED`、`NOT_CONNECTED` 对外值继续兼容，内部增加以下接入检查点：

1. `REGISTERED`：目录中存在官方根地址和路线归属；
2. `CONTRACT_VERIFIED`：列表入口、分页、文章链接、附件或 API 返回结构通过离线合同测试；
3. `LIVE_SMOKE_VERIFIED`：真实官网小范围访问成功，域名、状态码和内容类型符合预期；
4. `BACKFILL_RUNNING`：至少一个年度正在回采；
5. `PARTIAL`：存在可用记录，但年度未齐、页面遗漏、附件解析失败或运行部分失败；
6. `CONNECTED`：2024—2026 三个年度均完成发现和处理，最新增量复跑成功，且不存在阻断该来源可信使用的未解释失败；
7. `FAILED`：入口合同失效、持续访问失败或无法得到可信官方内容；
8. `NOT_CONNECTED`：仅登记、尚未进入验证。

`CONNECTED` 必须同时满足：

- `recruitment_source` 中存在可运行配置；
- 三个年度都有完成记录，即使某年度明确为零结果也要保存完成证据；
- 发现、下载和处理计数可对账；
- 所有失败都有工件级或行级记录；
- 同一输入复跑不会重复生成公告或岗位；
- 增量复跑结果可以区分 unchanged 与 updated。

启用 YAML、创建数据库行或人工修改目录状态，均不能单独满足 `CONNECTED`。

## 7. 第一批来源设计

### 7.1 杭州电子科技大学（HDU）

**官方入口：** `https://renshi.hdu.edu.cn/` 及其招聘列表。

**策略：** `STATIC_HTML`。

适配器应：

- 从招聘列表和历史分页发现 2024—2026 年公告；
- 将相对地址规范化为官方 HTTPS 地址；
- 使用文章 URL 规则、发布日期和标题范围过滤招聘公告；
- 保留公告正文中的岗位条件、报名方式和流程；
- 下载公告内 `.xls`、`.xlsx`、`.pdf`、`.doc`、`.docx` 附件；
- 将后续资格审查、考试和录用通知关联到原招聘事件；
- 对“教师/科研人员”纯教学岗位进行相关性标注，但不在采集阶段删除证据。

### 7.2 浙江工商大学（ZJGSU）

**官方入口：** `https://talents.zjgsu.edu.cn/rczp/list.htm`。

**策略：** `STATIC_HTML`。

该来源当前仅是 `PARTIAL`，本期不能重新造一条平行来源。应补齐实际 `recruitment_source` 配置、三年回采和增量运行，并复用已有目录代码 `ZJGSU_RECRUITMENT`。

适配器应：

- 验证列表分页和文章 URL 规则，不只抓当前第一页；
- 将校内官方详情与跳转到微信公众号的线索分开记录；微信公众号内容只有在确认属于学校官方账号且能保留稳定证据时才作为补充工件，不能覆盖校内官方事实；
- 抓取事业编、劳务派遣和其他用工公告，但将用工身份作为结构化事实；
- 下载岗位计划表和报名材料附件；
- 解析信息化建设、实验技术、网络与数据、行政技术支持等岗位；
- 保留公告正文和附件之间的证据关系；
- 当前栏目主要为博士后、高层次人才和外部微信公众号内容；若三年内没有足够的正式技术支持岗位证据，来源保持 `PARTIAL`，不得因已有 `enabled: true` 或能抓到链接升级。

### 7.3 杭州市第一人民医院

**历史官方入口：** `https://zp.hz-hospital.com/`。

**当前官方证据入口：** 医院主站、杭州卫健委、人社部门等发布市一医院招聘公告的 HTTPS 页面。

**报名链接：** `http://zhaopin.hz-hospital.com:8080/`，仅保存和展示，不自动请求。

**策略：** 新增 `HOSPITAL_OFFICIAL_EVIDENCE`，按年度路由到经过白名单验证的 HTTPS 官方公告入口。

适配器应：

- 2024 年从旧 HTTPS 招聘系统的公告列表和 `announcement_desc` 详情发现招聘批次；
- 解析旧系统详情页内已经公开的岗位需求表，包括科室、岗位、人数、学历学位、专业、招聘对象和年龄上限；
- 2025—2026 年从医院主站、杭州卫健委、人社部门等 HTTPS 官方栏目发现市一医院公告和后续考试通知；
- 对同一招聘批次的医院公告、主管部门公告和后续通知进行事件关联，不重复生成岗位；
- 将招聘批次、科室、岗位名称、人数、专业、学历学位、年龄、经历、报名截止和用工说明映射为统一工件；
- 若附件存在，继续走统一下载和文档处理管线；
- 将 HTTP 新系统地址保存为 `applicationUrl` 证据，但下载器必须拒绝对其发起请求；
- 任何年度缺少可验证的官方列表范围时标为 `PARTIAL`，不能制造空年度完成记录；
- 官方入口结构变化时进入 `FAILED` 或 `PARTIAL`，不得悄悄返回空列表。

所有自动请求必须使用 HTTPS、限速、设置超时和固定 User-Agent，并遵守官网公开访问边界。需要登录、验证码或仅 HTTP 的页面不在本期自动访问。

## 8. 历史回采与分页

每个来源按 2024、2025、2026 三个年度建立独立运行范围。发现器可以通过年度入口、分页遍历或抓取发布日期后筛选，但必须记录：

- 请求过的列表页和页码；
- 发现的候选链接数；
- 因年份、标题或重复而过滤的数量；
- 成功下载、未变化、更新、失败的工件数；
- 处理成功、部分成功、失败的岗位和附件数；
- 最早和最晚公告日期；
- 年度完成原因。

停止分页必须基于明确条件，例如空页、重复页、已越过目标年份或官方总页数；不能只抓固定前 N 页。发现到同一官方文章时按规范化 URI 去重。

历史回采与每日增量使用同一实现，仅运行范围不同。回采可以指定年份和分页上限；每日增量从最新页开始，遇到连续已知且未变化的页面后安全停止，但仍定期执行全量校验任务发现旧公告更新。

## 9. 稳定键、内容指纹和差异

### 9.1 工件稳定键

工件优先使用规范化官方 URI 作为稳定键。规范化只允许：

- 统一 scheme/host 大小写；
- 移除 fragment；
- 移除已知追踪参数；
- 对业务参数排序；
- 将确认等价的相对/绝对路径统一。

不得删除决定详情、分页、批次或岗位的业务参数。

### 9.2 岗位稳定键

岗位键优先级：

1. 官方岗位编号；
2. 官方招聘批次 + 单位/科室 + 岗位名称；
3. 公告稳定键 + 附件页/工作表 + 规范化行身份。

岗位名称、人数或条件变化应产生 `UPDATED`，不能生成新岗位。没有官方编号时，人数、资格条件和解析后的可变字段不得进入身份键。

### 9.3 内容指纹

- 原始正文和附件保存 SHA-256；
- 规范化岗位事实另存语义指纹；
- 原始内容变化但语义未变时，工件为 `UPDATED`，岗位可以保持 `UNCHANGED`；
- 语义指纹变化时，岗位为 `UPDATED` 并重新执行资格、评分和通知；
- 相同指纹复跑必须是 `UNCHANGED`。

### 9.4 下线判断

单次未发现、网络失败或列表结构变化不得判定下线。只有来源运行成功、扫描范围完整且同一岗位连续多次不再出现，或官网明确撤销时，才生成 `OFFLINE` 候选。历史公告默认归档，不因离开当前列表而下线删除。

## 10. 文档处理与部分失败

所有 HTML、PDF、Excel 和 Word 工件复用现有文档处理端口。Excel 导入必须支持行级隔离：

- 每一失败行记录来源、公告、附件、工作表、行号、错误阶段、错误代码和安全摘要；
- 成功行正常生成岗位；
- 附件整体状态为 `PARTIAL`；
- 修复解析器后可以只重放失败行或整个附件；
- 错误记录不得包含不必要的个人身份证号、手机号等敏感报名数据。

当前杭州市人社来源中尚存的 XLS 行解析问题也纳入相同错误账本，不能继续只以来源连续失败计数表达。来源访问失败、工件下载失败、文档解析失败和行解析失败必须分别统计。

## 11. 数据模型与配置

本期预计增加或扩展以下概念，具体字段由实施计划和迁移测试确定：

- `SourceAdapterType`：支持 `STATIC_HTML`、`JCMS_LISTING`、`HOSPITAL_OFFICIAL_EVIDENCE`；
- `SourceOnboardingCheckpoint`：保存接入检查点和验证时间；
- `SourceYearCoverage`：来源、年度、运行范围、计数、完成状态和原因；
- `ArtifactImportFailure`：工件级或行级失败；
- `RecruitmentSource` 配置：分页、标题过滤、详情请求合同、限速和历史年份；
- `TargetSourceCatalog`：状态由覆盖事实投影，不允许 YAML 直接宣布完成。

配置中不得保存登录凭据。公开 API 的可变请求字段应有白名单；响应中的未知字段忽略但记录合同漂移指标。数据库迁移必须可在现有 28 个 Flyway 迁移之上前向执行。

## 12. 数据流与重新计算

1. 调度器选择来源和年度范围；
2. 来源适配器发现官方工件；
3. 下载器获取内容并计算原始指纹；
4. 未变化工件直接结束，变化工件进入处理；
5. 文档处理器提取招聘事件、岗位、应届规则和考试流程；
6. 稳定岗位键和语义指纹生成岗位差异；
7. 受影响岗位重新执行资格判断和路线聚合；
8. 覆盖账本根据本次真实结果更新来源年度状态；
9. 目标来源目录投影 `CONNECTED`、`PARTIAL` 或 `FAILED`；
10. `/opportunities`、岗位详情、规划页和 `/updates` 展示新增/变更及新覆盖证据。

同一次运行使用幂等运行键；重复提交不得生成重复工件、岗位、事件或通知。

## 13. 错误处理与可观测性

错误至少区分：

- `DISCOVERY_CONTRACT_CHANGED`：列表或 API 合同变化；
- `REMOTE_ACCESS_FAILED`：超时、DNS、TLS、4xx/5xx；
- `ARTIFACT_DOWNLOAD_FAILED`：附件下载失败；
- `UNSUPPORTED_DOCUMENT`：文档类型不支持；
- `DOCUMENT_PARSE_FAILED`：文件整体无法解析；
- `ROW_PARSE_FAILED`：单行无法转换；
- `NORMALIZATION_FAILED`：稳定键或字段规范化失败；
- `EVIDENCE_LINK_FAILED`：岗位与公告/附件无法关联。

每次运行输出来源、年度、耗时、请求数、发现数、下载数、处理数、差异数、失败数和停止原因。访问失败保留上次成功数据并展示陈旧时间；不清空岗位，不制造下线。

## 14. 测试策略

### 14.1 测试驱动顺序

所有实现先写失败测试，再写最小实现。禁止以真实官网不稳定为由只做人工验收。

### 14.2 离线合同与夹具

为三个来源保存去除个人敏感信息的最小 HTML/JSON/附件夹具，覆盖：

- 多页列表与相对链接；
- 2024—2026 年过滤；
- 公告详情和多个附件；
- 医院旧系统公告详情内的岗位表，以及 2025—2026 年 HTTPS 官方公告；
- HTTP 报名链接只保存不请求；
- 重复文章和规范化 URI；
- 内容未变与内容更新；
- Excel 成功行和失败行并存；
- 空页、合同变化和远程失败。

### 14.3 分层测试

- 领域测试：稳定键、指纹、差异、下线门控和状态投影；
- 应用测试：年度回采编排、部分失败、幂等和重新计算；
- 基础设施测试：HTML/JSON 适配器、附件解析、数据库迁移和覆盖账本；
- API 测试：来源状态、年度覆盖、机会与更新差异；
- 前端测试：高校/医院覆盖、未知原因、增量变化和官方证据链接；
- 真实浏览器测试：使用本地数据库从规划页进入岗位详情和官方证据。

### 14.4 真实官网冒烟

真实官网测试作为显式的 opt-in 验收任务，不进入每次离线单元测试。每个来源至少验证：

- 官方域名和证书有效；
- 当前列表/接口可读；
- 至少一个详情或附件可获取；
- 实际内容通过对应适配器；
- 请求频率和失败重试符合边界。

真实官网失败时不得修改夹具让测试虚假通过，应将来源留在 `PARTIAL` 或 `FAILED`。

## 15. 验收标准

本期完成必须同时满足：

1. HDU、ZJGSU、杭州市第一人民医院都存在正式、可调度的 `recruitment_source`；市一医院来源只能调度 HTTPS 官方证据入口；
2. 三个来源分别有 2024、2025、2026 年覆盖记录；
3. 只有真实完成三年回采和最新增量复跑的来源才为 `CONNECTED`；
4. 目标来源统计从现有 2 个 `CONNECTED`、1 个 `PARTIAL` 得到真实提升；若三源均通过验收可达到 5 个 `CONNECTED`，但 ZJGSU 或市一医院因官方证据范围不足而保持 `PARTIAL` 是可接受且必须如实展示的结果；
5. 每个来源至少有一个真实公告或岗位进入站内详情；若官方年度确实无相关岗位，需有零结果完成证据；
6. 公告正文、附件、岗位和流程事实可追溯到官方 URL；
7. 同一数据连续运行两次，第二次不产生重复新增；
8. 修改夹具中的岗位条件后只产生对应 `UPDATED`；
9. 单行 Excel 失败不会阻止其他行入库，失败行可在系统中审计；
10. 网络失败保留旧数据，不产生虚假下线；
11. 用户 `01992f09-0000-7000-8000-000000000001` 的高校/医院路线使用新数据重新计算，并展示样本、年份和来源；
12. 全量后端测试、前端测试、TypeScript 检查、生产构建、数据库迁移、API 验收和真实浏览器验收全部通过。

如果医院 HTTPS 官方入口无法取得三年数据，医院来源应保留 `PARTIAL`，同时交付已验证的安全采集能力和清晰缺口。ZJGSU 也遵循相同规则。任一来源保持 `PARTIAL` 不阻止其他来源完成，但不能宣称第一批达到 5 个完整来源。

## 16. 后续批次

第一批验收后，第二批按用户价值和来源可行性依次接入：余杭区、滨江区、钱塘区和萧山区官方招聘栏目。后续高校、医院、科研院所和国企仍使用相同生命周期和验收规则，每批单独设计、回采和验收。

第一批留下的适配器边界、覆盖账本和行级错误模型必须能支持后续来源，而不要求复制完整采集管线。
