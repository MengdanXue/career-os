# Career OS 资格正确性、考试流程与市场覆盖整改设计

**日期：** 2026-08-24  
**状态：** 已完成对话设计确认，待书面规格复核  
**目标用户：** 测试候选人，1992-12-31 出生，计算机本科已完成，示例海外大学计算机科学硕士预计 2027 年毕业，目标为杭州/浙江半体制稳定技术岗位

## 1. 背景与问题

当前系统能够保存官方公告、解析部分岗位附件、生成历史规划并展示岗位详情，但尚未可靠回答用户最核心的问题：2027 年是否以境外硕士应届生身份报考、具体岗位是否可报、什么时候报名、是否笔试以及如何准备。

已确认的产品缺陷如下：

1. 历史公告中的绝对毕业年份被直接用于目标年份预测。2026 岗位允许 2024—2026 届时，系统会因候选人预计 2027 年毕业而判定不符合；这对历史岗位实际报名判断成立，但对 2027 同类岗位预测不成立。
2. `PRE_GRADUATION` 被展示为“本科阶段”，混淆“已完成最高学历”和“当前硕士在读状态”。
3. 应届身份、境外学历认证、证书取得期限、未落实工作单位和社保限制没有形成独立且可解释的规则模型。
4. 招聘事件已经保存部分报名、笔试和面试字段，但规划聚合只统计笔试科目，未形成完整招聘流程与准备日历。
5. `DataCoverage.complete` 仅表示已配置来源年度全部完成，却容易被理解为浙江/杭州目标市场覆盖完整。
6. 当前正式采集源主要是浙江省人社厅和杭州市人社局，政府国企、科研院所、高校、医院及区县独立官网覆盖不足；零样本路线因此不能参与实质排名。
7. “官网未明确”“系统未采集”“解析失败”“待人工复核”没有被清楚区分。

本整改不能通过修改文案解决。它需要统一资格语义、公告规则、来源覆盖、考试流程和用户界面。

## 2. 产品目标

系统必须基于官方证据，围绕用户的目标年份与真实画像直接回答：

1. 用户是否属于目标招聘年度的应届毕业生候选范围；
2. 当前、取得境外学位后、完成留服认证后三个认证阶段分别能否报考；
3. 历史岗位当年实际资格与未来同类岗位预测资格有何区别；
4. 岗位报名、资格审查、缴费、准考证、笔试、专业测试、面试、体检、公示和聘用流程；
5. 每项结论来自哪份官方公告、附件或官方招聘系统；
6. 哪些路线确实没有目标岗位，哪些只是尚未接入或尚未完成采集；
7. 2027—2028 两个关键周期应该监控什么、准备什么、何时行动。

## 3. 设计原则

1. **历史事实与未来推演分离。** 历史岗位保留原始年份和当年实际资格；未来推演只转换可安全归一化的相对规则。
2. **应届身份与学历认证正交。** “是不是目标届毕业生”和“硕士/留服是否在截止日前取得”分别判断，再合并为资格结论。
3. **官方证据优先。** 官方公告、官方附件、官方报名系统和单位官网是资格结论依据；第三方聚合站只用于发现线索和交叉检查。
4. **未知不等于否定。** 未采集、未公布、解析失败、候选人事实未知和规则歧义必须有不同状态。
5. **无市场覆盖时不排名。** 零样本路线只有在目标来源目录和对应年份完成覆盖后，才允许解释为没有目标岗位。
6. **确定性规则优先。** Java 规则引擎负责年龄、学历、专业、届别、认证期限、经历、政治面貌和职称；LLM 不得改写硬资格结论。
7. **用户先看到行动。** 页面优先展示能否报、下一截止日期、考试流程和准备动作，再展示采集技术细节。

## 4. 方案取舍

### 4.1 采用：规则、证据与覆盖一体化整改

在现有领域、应用、基础设施和 React 工作台上增加独立的应届规则模型、目标年份投影、招聘流程事实、三层覆盖范围和来源目录。该方案改动较大，但能够形成可复算、可解释和可持续增量更新的产品闭环。

### 4.2 不采用：只修规划页判断和文案

该方案可以快速把“本科阶段”改成“硕士在读”，也可以把部分不可报改成条件可报，但无法解决来源缺失、届别投影、考试流程和证据状态混淆，后续新公告仍会重复出错。

### 4.3 不采用：让 LLM 直接阅读网页并回答

LLM 可辅助识别规则原文和生成解释，但不能稳定处理截止日期、绝对年份、相对届别、认证阶段和社保限制，也无法提供可重复运行的增量差异和审计证据。

## 5. 资格模型

### 5.1 教育认证阶段

保留三个教育认证阶段，但修正名称：

- `MASTER_IN_PROGRESS`：本科已完成，境外硕士在读、预计取得；
- `DEGREE_PENDING_VERIFICATION`：境外硕士学位已取得，留服认证待完成；
- `MASTER_VERIFIED`：境外硕士学位与留服认证均已完成。

旧 `PRE_GRADUATION` API 值在兼容期内可以保留，但展示名称、解释和内部规则不得继续称为“本科阶段”。新算法版本输出 `MASTER_IN_PROGRESS`；前端在兼容期同时识别旧值。

### 5.2 应届身份轨道

新增独立的 `GraduateEligibilityTrack`：

- `TARGET_YEAR_GRADUATE`：预计毕业年份等于规划目标年份；
- `RECENT_GRADUATE_WINDOW`：属于公告允许的前一届或前两届范围；
- `NOT_IN_GRADUATE_SCOPE`：有明确证据不在允许届别；
- `CONDITIONAL`：取决于学位、留服、未就业、社保或档案条件；
- `UNKNOWN`：公告规则或候选人事实不足。

候选人预计 2027 年毕业时，在 2027 规划中首先进入 `TARGET_YEAR_GRADUATE`，不能因为历史样本来自 2026 年而直接判定不符合。

### 5.3 公告届别规则

新增 `GraduateRule`，至少包含：

- 原始规则文本和官方证据定位；
- 招聘年度；
- 明确列出的毕业年份；
- 相对届别：当届、前一届、前两届或不限；
- 是否包含同期留学回国人员；
- 学历学位取得截止阶段与日期；
- 留服认证截止阶段与日期；
- 是否要求未落实工作单位；
- 是否限制社保、劳动关系或档案状态；
- 解析状态与人工复核状态。

绝对年份只用于历史岗位实际判断。未来预测使用相对届别；不能可靠归一化时输出 `UNKNOWN`，并保留原文。

### 5.4 双模式资格判断

同一个历史岗位提供两种结论：

- `HISTORICAL_ACTUAL`：按公告原年份和候选人在该年度的事实判断，用于复盘；
- `TARGET_YEAR_ANALOG`：将安全归一化的届别、月份窗口和考试流程投影到目标年份，用于规划，不声称未来公告一定相同。

例如，2026 岗位仅接受 2024—2026 届：

- 对 2026 实际岗位，2027 毕业生为不可报；
- 对 2027 同类岗位推演，2027 届候选人属于当届，应根据学位和留服截止要求输出可报、条件可报或待确认。

### 5.5 资格合并顺序

每个岗位按以下顺序合并：

1. 用工身份和目标范围；
2. 年龄；
3. 学历与学位；
4. 专业；
5. 应届届别；
6. 境外学历与留服认证期限；
7. 未就业、社保、劳动关系和档案要求；
8. 工作经历；
9. 政治面貌、性别、户籍和职称；
10. 其他公告条件与证据完整度。

每个维度输出 `PASS`、`CONDITIONAL`、`UNKNOWN` 或 `FAIL`，总结果仍为 `ELIGIBLE`、`CONDITIONALLY_ELIGIBLE`、`UNCERTAIN` 或 `INELIGIBLE`。`FAIL` 必须引用明确规则，未知信息不得产生 `FAIL`。

## 6. 招聘与考试流程

### 6.1 招聘事件里程碑

`RecruitmentEvent` 的流程读模型覆盖：

- 公告发布日期；
- 报名开始与截止时间；
- 报名入口；
- 资格初审截止；
- 缴费截止；
- 准考证下载开始与截止；
- 笔试日期、时间、地点说明；
- 笔试科目；
- 是否有笔试；
- 是否有专业/业务/技能测试；
- 面试通知日期、面试日期、形式和入围比例；
- 成绩计算方式；
- 体检、考察、公示与聘用说明。

已有字段继续复用；不存在的字段通过向后兼容迁移补充。事件级规则和岗位级专业测试条件分别保存，不互相覆盖。

### 6.2 信息状态

每个关键流程字段必须携带以下状态之一：

- `CONFIRMED`：官方证据明确；
- `NOT_PUBLISHED`：公告明确说明另行通知或尚未发布；
- `NOT_REQUIRED`：公告明确不需要该环节；
- `NOT_COLLECTED`：目标页面或附件尚未采集；
- `PARSE_FAILED`：已有原件但解析失败；
- `REVIEW_REQUIRED`：存在歧义或冲突；
- `UNKNOWN`：无法进一步区分。

前端不得把上述状态统一显示为“官网未明确”。

### 6.3 历史考试统计

考试统计以独立招聘事件为分母，至少输出：

- 有笔试、无笔试、未知的事件数和比例；
- 各笔试科目的事件数；
- 有专业测试的事件数；
- 结构化面试、实操、答辩、试讲及其他形式的事件数；
- 报名截止到笔试的天数分布；
- 公告、报名、笔试、面试月份分布；
- 每项统计使用的来源、年度、事件数和缺失数。

日期缺失时不插值，不把“另行通知”算作没有面试。

## 7. 来源目录与采集覆盖

### 7.1 目标来源目录

建立可审计的 `TargetSourceCatalog`。首批至少接入 20 个官方来源，按路线覆盖：

1. 浙江省人社厅与杭州市人社局；
2. 滨江、余杭、钱塘、萧山等重点区政府或人社招聘栏目；
3. 杭州重点高校招聘官网；
4. 杭州市属、省属医院招聘官网；
5. 科研院所、实验室和新型研发机构官网；
6. 杭州数据集团及市属、省属国企官方招聘系统。

每个来源记录组织类型、路线、地区、权威级别、入口类型、历史年份入口、当前招聘入口、抓取方式、启用状态和自动化限制。

### 7.2 证据优先级

1. 官方公告正文；
2. 官方附件；
3. 官方报名系统或后续考试通知；
4. 招聘单位官网的补充通知；
5. 政府或主管部门转载；
6. 第三方聚合页，仅作发现线索。

低优先级来源不能覆盖高优先级事实。出现冲突时保留双方证据并进入复核。

### 7.3 三层覆盖语义

规划 API 和页面同时输出：

- `configuredCoverage`：已经配置的来源年度是否扫描完成；
- `targetMarketCoverage`：目标来源目录中已接入、部分、失败、未接入的数量，按路线和年份分组；
- `analysisCoverage`：当前结论实际使用的来源、年份、事件、岗位和关键字段证据覆盖率。

现有 `complete` 字段在兼容期内更名解释为 `configuredSourcesComplete`。页面禁止使用“市场数据完整”等文案。

### 7.4 路线排名门控

路线存在以下状态：

- `RANKED`：来源覆盖和分析样本达到最低门槛，可参与路线比较；
- `LIMITED`：可以展示描述性统计，但排名证据有限；
- `NOT_COVERED`：目标来源未接入，不参与排名；
- `NO_TARGET_RECORDS`：来源与年度覆盖完成且确认没有目标岗位；
- `DATA_FAILURE`：采集或读取失败，不参与排名。

`NOT_COVERED`、`DATA_FAILURE` 不能显示 0 分。`NO_TARGET_RECORDS` 必须有完整覆盖账本支持。

## 8. 增量采集与数据融合

1. 复用现有稳定公告键、岗位键、SHA-256 内容指纹和新增/变更/下线差异。
2. 公告正文、岗位附件、报名通知、笔试通知和面试通知作为同一招聘事件的多个官方工件关联。
3. 后续通知只补充或更新对应流程字段，不复制生成新的岗位。
4. 同一字段的新官方证据导致内容指纹变化时，撤销旧自动准入并重新评估受影响岗位。
5. 抓取失败保留上次成功结果，显示陈旧时间和失败来源；不能把短期访问失败解释为岗位下线。
6. 第三方来源发现的 URL 必须回到官方域名采集后，才进入资格和考试结论。

## 9. API 与页面

### 9.1 规划 API

`CareerPlan` 增加：

- 候选人的目标年度应届轨道；
- 教育认证阶段和应届身份的组合结果；
- 历史实际与目标年份同类岗位两种结论；
- 招聘考试统计及分母；
- 三层覆盖范围；
- 路线排名状态和暂停原因；
- 算法与规则版本。

### 9.2 规划首页

首页首先显示：

1. “2027 届境外硕士应届生候选”结论与条件；
2. 应届通道和社会人员通道；
3. 2027—2028 年龄及毕业窗口；
4. 重点招聘月份和典型考试流程；
5. 当前需要准备的证据和考试内容；
6. 每条路线的市场覆盖状态。

无覆盖路线显示“尚未接入目标来源，暂不排名”，不能显示为最后一名或 0 分。

### 9.3 岗位详情

岗位详情站内完整展示：

- 历史事实；
- 目标年份同类岗位推演；
- 每个资格维度及原因；
- 应届与留服规则原文；
- 全部已知招聘流程；
- 每个未知字段的真实原因；
- 官方公告、附件、报名系统和后续通知链接。

历史公告已截止时必须明确标记，不显示为当前报名机会。

### 9.4 行动工作台

当未来公告出现后，系统基于正式日期生成：

- 资格复核任务；
- 报名截止提醒；
- 缴费和准考证提醒；
- 笔试科目准备任务；
- 专业测试和面试准备任务；
- 留服认证或工作经历证明任务。

没有可信机会时仍需展示画像、材料和历史考试准备动作，不能让“今日行动”完全空白。

## 10. 实施切片

### Slice A：资格正确性

- 修正硕士在读场景；
- 增加应届轨道与公告相对届别规则；
- 区分历史实际和目标年份同类岗位判断；
- 用用户真实画像建立回归测试。

### Slice B：流程事实与考试统计

- 扩展公告解析和招聘事件流程字段状态；
- 关联后续笔试、面试通知；
- 提供完整考试统计与岗位时间线。

### Slice C：市场覆盖与来源扩张

- 建立目标来源目录和三层覆盖 API；
- 首批接入至少 20 个官方来源；
- 补采 2024—2026 并启用当前增量采集；
- 无覆盖路线退出排名。

### Slice D：用户闭环

- 重构规划首页、岗位详情与今日行动；
- 展示应届/社会双通道；
- 用真实浏览器完成端到端验收。

每个切片必须独立通过领域、持久化、API 和前端测试后才能进入下一切片。不得用后续切片掩盖当前切片失败。

## 11. 测试策略

### 11.1 领域与应用测试

至少覆盖：

1. 2027 境外硕士预计毕业生面对 2026 历史岗位，实际判断为不可报但 2027 同类推演进入当届应届范围；
2. 2027 当届岗位允许当年指定日期前取得学位时，硕士在读场景为条件可报；
3. 留服认证必须在报名截止前完成时，待认证场景不可报；
4. 留服允许资格复审或聘用前补齐时，待认证场景为条件可报；
5. 有“未落实工作单位”或社保限制时只按明确证据判断；
6. 过去工作经历不自动取消新取得硕士时的当届身份；
7. 无覆盖路线不产生 0 分排名；
8. 只有完整覆盖支持 `NO_TARGET_RECORDS`；
9. “另行通知”不等于无笔试或无面试；
10. 同一事件的后续通知只更新流程，不复制岗位。

### 11.2 Golden Dataset

建立至少 10 组官方公告与附件，覆盖：

- 杭州市属事业单位统一招聘；
- 境外应届生与留服规则；
- 本科社会人员岗位；
- 硕士应届岗位；
- 有笔试和面试；
- 只有面试或专业测试；
- 后续单独发布笔试/面试通知；
- 高校、医院、科研院所和国企正式岗位。

每组人工标注届别、认证期限、报名、笔试、面试、用工身份和证据定位。

### 11.3 API 与前端测试

- API 合同测试覆盖新旧字段兼容；

## 12. 最终验收

使用候选人 `01992f09-0000-7000-8000-000000000001`，系统必须在站内直接给出：

1. 当前为“境外硕士在读，预计 2027 届”，不是“本科阶段”；
2. 2027 应届技术岗属于重点通道；
3. 对历史岗位分别展示当年实际结论和 2027 同类岗位推演；
4. 明确列出学位与留服认证的截止条件；
5. 展示报名、资格审查、缴费、准考证、笔试科目、专业测试和面试信息；
6. 对信息缺口说明是未公布、未采集、解析失败还是待复核；
7. 政府国企和科研路线未覆盖时不显示 0 分；
8. 展示市场来源接入度，不能把两个配置来源写成市场完整；
9. 即使可信机会池暂时为空，也能生成材料与考试准备行动；
10. 全量后端测试、前端测试、生产构建和真实浏览器流程均通过。

只有以上十项全部有新鲜验证证据时，才允许称本整改完成。采集成功、数据库记录很多或单元测试通过都不能单独作为完成标准。

## 13. 非目标与边界

- 不自动报名或投递；
- 不绕过登录、验证码或网站访问限制；
- 不用第三方聚合信息生成确定资格结论；
- 不展示未经校准的录取概率；
- 不把预计政策当作未来官方承诺；
- 不自动把简历中的概括工作年限变成已核验报考年限。
