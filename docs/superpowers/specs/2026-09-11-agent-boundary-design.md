# Career OS Agent 边界设计

日期：2026-09-11
状态：设计提案，未实施

## 1. 现状判断

Career OS 目前**不是 agent 产品**，是一个证据优先的确定性决策引擎，LLM 出现在两个边缘位置：

| 位置 | 作用 | 约束方式 |
| --- | --- | --- |
| `OpenAiStructuredExtractor` | 从 HTML/PDF 抽取结构化提案 | 类型转换 + JSON Schema + 领域校验 + 证据校验，**四道确定性闸门** |
| `AgentPhraser` | 润色已经算好的答案 | **只有 prompt 里的一句话**："不得修改资格、层级、分数" |

这个格局大体是对的。产品需求 §39 明令「LLM 不得覆盖硬规则结果，也不得在缺少证据时把"未知"改成"满足"」，
基线 §11 把「用 LLM 猜测专业等同性或编制身份」列为非目标。因此**不该**为了"像个 agent"而把模型放到
结论链路上。

但"不是 agent"目前有三处是真缺陷，不是刻意取舍：

### A. 问题理解是关键词 `contains()`

`AgentQueryService` 用 `q.contains("杭州")`、`q.toUpperCase().contains("T1")`、`lower.contains("java")`
把自由问题映射到排序参数。"临平的信息中心岗还有哪些没截止的"会被理解成
`location=null, jobFamily=INFORMATION_SYSTEMS`——区县丢了，截止条件丢了。

### B. 对模型输出没有校验闸门

抽取路径有四道闸门，对话路径一道都没有。`AgentPhraser` 拿到确定性答案和结构化摘要，
返回一段自由文本，系统**直接展示**。模型多说一个数字、把"条件可报"写成"可报"、把覆盖率
说成上岸概率——没有任何机制会发现。基线 §6.2 明确禁止「把主观分数伪装成统计概率」，
而现在唯一的防线是 prompt 里的一句请求。

### C. 没有闭环：系统知道要问什么，但不会问

`EligibilityEvaluator` 有 27 处 `needsConfirmation(...)`。
`CandidateEvidenceTaskService` 已经有 `KIND_PRIORITY`，`QualificationImpact.affectedJobCounts`
已经算出**每个未确认事实卡住多少个岗位**。

但这些只被渲染成一个待办列表。系统知道"确认留服认证状态能解锁 23 个岗位"，却不会主动
把这件事提到用户面前、不会在用户回答后自动重算、不会记得上次问到哪。

这是"仪表盘"和"agent"的真正分界：**仪表盘展示状态，agent 推进状态**。

## 2. 设计原则：模型规划与叙述，绝不下结论

基线 §7 其实已经写清楚 agent 该干什么：

> Agent 负责：根据用户目标规划需要调用的工具；处理公告中不规则文本和含糊表述；
> 汇总证据、解释结论和提出待确认问题；在规则冲突或证据不足时主动降级结论。

注意这几件事**没有一件是"做出判定"**。所以本设计的边界是：

> **LLM 选择调用哪些确定性工具、以什么顺序调用，并把工具返回值组织成回答。
> 回答里每一个事实、判定、分数、层级都必须能追溯到某个工具的返回值，
> 且在展示前由确定性代码校验。**

这与抽取路径是同一个模式：**模型提议 → 确定性校验 → 不通过就降级或拒绝**。
抽取路径已经这么做了；对话路径还没有。本设计的核心就是把这个模式补到对话路径上。

## 3. 架构

```
用户问题
   │
   ▼
┌─────────────────────────────────────────┐
│ L2 规划器（LLM）                         │
│   在固定工具集里选工具 + 填类型化参数      │
│   受前置条件图约束，不能跳步              │
└───────────────┬─────────────────────────┘
                │ 工具调用
                ▼
┌─────────────────────────────────────────┐
│ L1 工具层（确定性，绝大部分已存在）        │
│   基线 §7 的 10 个工具                   │
│   返回值全部带证据 ID                     │
└───────────────┬─────────────────────────┘
                │ 工具返回值（唯一事实来源）
                ▼
┌─────────────────────────────────────────┐
│ L3 叙述器（LLM）→ 断言校验器（确定性）★   │
│   模型起草回答                            │
│   校验器逐条比对：回答里的每个数字/判定     │
│   是否出现在工具返回值里                  │
│   对不上 → 丢弃该句 或 整体回落确定性模板  │
└───────────────┬─────────────────────────┘
                ▼
┌─────────────────────────────────────────┐
│ L4 待确认闭环                            │
│   按 affectedJobCounts 选最小提问集       │
│   记录回答 → 触发重算 → 报告变化          │
└─────────────────────────────────────────┘
```

★ 是目前完全缺失、且价值最高的一层。

### L1 工具层

基线 §7 已经列出 10 个工具。主干里绝大部分已有对应服务，需要的是把它们收敛成一个稳定的
工具面，而不是重写：

| 基线工具 | 主干现有实现 |
| --- | --- |
| `scan_sources` | `AcquisitionService` |
| `download_artifact` | `AcquisitionService` + `artifact_discovery` |
| `parse_document` | `MediaTypeDocumentParser`（HTML/PDF/DOCX/Excel/ZIP） |
| `normalize_job` | `JobUpsertService.NormalizedJob` |
| `calculate_delta` | `JobUpsertResult.changes`（本轮刚加） |
| `classify_employment_identity` | `OfficialJobAdmissionService` + `EmploymentType` |
| `evaluate_eligibility` | `EligibilityEvaluator`（9 条规则） |
| `score_opportunity` | `FitEvaluator` / `StabilityEvaluator` / `AssessmentDimension` |
| `link_history` | `JobLineageBuilder` / `OpportunityForecaster`（本轮刚加） |
| `generate_watchlist` | `OpportunityHistoryService.watchlist` |

**不要复用 `agent-app` 里那 7 个 `@Tool`**。它们是 phase-0 的工具（`scan_official_recruitment_sources`
只扫 S09/S10 国企源、`find_it_job_candidates` 只做 IT 关键词相关度），`docs/current-gap-analysis.md`
已经把它们列为必须重构。`agent-app` 保持隔离，新工具面建在主干服务之上。

**前置条件图**：`agent-app` 的工具描述里写了"必须在扫描工具之后调用"——那是散文，模型可以无视。
改成声明式前置条件，规划器产出的计划在执行前由确定性代码检查，跳步直接拒绝重规划。

### L3 断言校验器（本设计的核心）

校验器不理解语义，只做机械比对，因此本身不会引入新的不确定性：

1. **数字**：抽取回答里所有数字，每一个必须在工具返回值里出现过（分数、覆盖率、人数、年份、天数）。
   出现在返回值之外的数字 = 模型编的。
2. **判定词**：`可报 / 条件可报 / 待确认 / 证据冲突 / 不可报`、`T1/T2/T3`、
   `RECOMMENDED/REVIEW/NOT_RECOMMENDED/EXCLUDED` —— 每次出现都必须绑定到一个具体岗位，
   且与该岗位工具返回的枚举值一致。说"可报"而工具返回 `CONDITIONAL` 即为不一致。
3. **禁用表述**：`概率`、`几率`、`把握`、`稳了`、`录取率` 一律拒绝——基线 §6.2 禁止把主观分数
   伪装成统计概率。
4. **证据**：回答里提到的每个岗位，其结论必须有 `RuleResult.evidenceIds` 或评估级
   `evidenceIds`（本轮刚接通的逐条证据链正好是这层的基础）。

不通过时的行为，按严重度分级：

- 单句对不上 → 丢弃该句，其余保留，标注"已移除 1 句无法核对的表述"
- 判定词不一致 或 出现禁用表述 → **整体回落到确定性模板**，不展示模型输出
- 两次回落 → 该会话本轮关闭模型润色，只用模板

校验失败要落库（复用 `review_item` 的形态），否则没人知道模型在偏向哪个方向出错。

### L4 待确认闭环

这是最像 agent、也最贴合本产品瓶颈的一层。

现有材料已经够了：`QualificationImpact.affectedJobCounts` 知道每个未确认事实卡住多少岗位，
`CandidateEvidenceTaskService.KIND_PRIORITY` 知道类别优先级，
`CandidateDecisionDiffService` 知道确认之后哪些结论变了。

要补的是把它们接成循环：

1. **选问题**：按"解锁岗位数 × 是否有截止临近"排序，一次只问 1–3 个，不倒一整个列表。
2. **问**：给出为什么问（"确认这项后 23 个 T1 岗位的资格结论能从待确认变成明确"）。
3. **记**：回答写进 `candidate_fact_confirmation`；不确定的答案允许留"仍不确定"，不逼用户猜
   —— 基线 §2.2 的字段本来就不得猜测。
4. **重算**：触发受影响岗位的决策重算（`evaluatorVersion` 机制已经能让快照失效）。
5. **报**：用 `DecisionChangeSummary` 报告"因为你确认了 X，这些岗位从待确认变成了可报"。

这一层**不需要 LLM 也能工作**，LLM 只负责把问题问得像人话。这一点很重要：闭环的正确性
不依赖模型。

## 4. 实施顺序

按"价值 ÷ 风险"排，不按架构层次排。

### 阶段一：断言校验器（最高优先）

只动 `AgentQueryService` + 新增校验器，不碰工具层，不引入规划器。
立刻消除"模型可以静默篡改结论"这个当前最大的正确性风险。

验收：构造模型返回篡改分数、把 `CONDITIONAL` 说成"可报"、说"上岸概率 70%" 三类响应，
断言系统分别丢句、回落、拒绝，并落一条校验失败记录。

### 阶段二：待确认闭环

不引入任何新的 LLM 调用。把已有的 impact 计算接成「选问题 → 记录 → 重算 → 报变化」。
这一步把产品从"仪表盘"变成"会推进的助手"，而且不承担模型风险。

验收：确认一项事实后，受影响岗位的结论真的重算并在变化摘要里出现；未确认时不产生
任何"可报"结论。

### 阶段三：工具面 + 前置条件图

把 L1 的 10 个工具收敛成稳定契约，声明前置条件。此时还没有规划器，工具面先被
阶段二的闭环和现有 REST 调用使用。

验收：跳步调用被确定性拒绝；每个工具返回值都带证据 ID。

### 阶段四：规划器

最后才引入 LLM 选工具。此时校验器、闭环、工具契约都已就位，模型即使规划错了也炸不出
错误结论——最坏情况是计划被前置条件拒绝、回答被校验器回落。

验收：多轮问题（"临平有哪些没截止的信息中心岗" → "第二个为什么是待确认"）能正确规划，
且任何一轮的回答都通过校验器。

## 5. 明确不做

- **不让模型做判定**。资格、层级、分数、用工身份永远来自确定性代码。
- **不做自动投递**。基线 §11 非目标。
- **不复用 `agent-app` 的工具**。它们偏离目标市场，gap analysis 已列为必须重构。
- **不为了"多 agent"而拆成 9 个 agent**。master spec §29–38 的 9 个 Agent 是职责划分，
  不必是 9 个独立的模型循环；绝大多数应该是确定性服务，只有需要处理不规则文本的那几个
  才涉及模型。基线 §11 把"复杂多 Agent"列为非目标。

## 6. 与现有文档的关系

- 本设计不改变 `docs/product-requirements.md` 的任何约束，是在它的约束下定义 agent 边界。
- `docs/CAREER_OS_MASTER_SPEC.md` §29–38 列了 9 个 Agent；本设计主张其中多数应实现为确定性
  服务而非模型循环，这一点与 §39「Java Rule Engine / LLM 边界」一致。
- 阶段一的校验器与 Phase 2 抽取路径的 Schema/证据校验是同一模式，可复用 `review_item`
  的失败留痕形态。
