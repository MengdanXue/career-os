# 杭州目标来源全量接入设计

日期：2026-08-27

状态：用户已批准

## 1. 目标

将 Career OS 目录中的 28 个杭州目标官方来源全部纳入可审计采集体系，消除 `NOT_CONNECTED` 与 `FAILED` 状态，并对每个来源执行真实增量采集、2024—2026 历史回填、附件解析、招聘生命周期关联和重复运行验收。

“来源接入完成”不等于伪造历史完整性。若官网本身没有可遍历档案、旧域名已经失效、栏目迁移导致官方总量无法证明，来源可以完成当前采集器接入，但对应年份必须保持 `PARTIAL`，并记录可验证的停止原因和缺口证据。

## 2. 完成标准

每个目标来源必须同时满足以下条件，才可以从 `NOT_CONNECTED` 或 `FAILED` 转为已接入状态：

1. 官方入口、详情链接模式、分页契约和附件域名已经核验。
2. 采集配置已登记，且只允许访问该来源明确列出的官方主机和路径。
3. 一次真实增量运行成功发现并处理候选公告；若当前窗口确无候选公告，必须通过已核验的空列表契约证明，而不是把首页零链接当成成功。
4. 第二次增量运行不产生重复新增；相同内容必须计入 `unchanged`。
5. 2024、2025、2026 三个年度均执行历史回填，并保存页数、过滤数、失败数、最早/最晚发布日期和停止原因。
6. 只有遍历官方报告总数或达到可证明的末页，且下载、解析和目标岗位计数一致时，年度才可标记为 `COMPLETE`。
7. 招聘公告与资格复审、成绩、笔试、面试、体检、考察、递补、公示、聘用等生命周期材料分别保存，并只在唯一匹配时关联。
8. 岗位表附件能够解析；非岗位工作簿、专业目录和说明表不得制造伪岗位或失败噪声。
9. UI 能展示来源状态、年度覆盖、失败原因、生命周期计数、岗位必要条件和官方证据链接。

全市场批次完成标准：28 个目标来源中 `NOT_CONNECTED=0`、`FAILED=0`。`PARTIAL` 仍可存在，但必须表示官网可验证的历史缺口，而不能表示未配置、未运行或当前运行失败。

## 3. 方案选择

### 3.1 采用方案：来源契约驱动的适配器联邦

在现有采集领域模型和增量指纹机制上扩展来源契约。共享分页、发现、下载、解析和覆盖证明能力，差异通过来源配置表达；仅对无法由通用契约表达的页面增加小型专用适配器。

优点：

- 同类官网共享一套经过测试的实现。
- 每个来源仍有独立的主机白名单、链接正则、分页上限和完成证据。
- 新来源接入以配置为主，不会复制二十套爬虫。
- 失败和完整性结论继续进入现有审计模型。

### 3.2 未采用方案：每站一个专用爬虫

短期接入速度可能较快，但分页、重试、附件和生命周期逻辑会重复，后续官网变更需要同时维护大量实现，因此不采用。

### 3.3 未采用方案：所有来源统一使用浏览器自动化

浏览器只作为动态站点和验收工具。常规采集继续使用受限 HTTP 客户端，因为浏览器运行成本更高、失败面更大，也难以提供稳定的官方总数与末页证明。

## 4. 架构

### 4.1 多入口来源契约

一个逻辑来源可以配置多个 `listingEntries`。每个入口包含：

- 唯一入口代码；
- 官方列表 URI；
- 入口角色：`PRIMARY`、`HISTORICAL`、`SECTOR`、`LIFECYCLE` 或 `CAMPAIGN_STATE`；
- 分页模式及参数；
- 详情链接正则；
- 标题包含与排除规则；
- 适用年度；
- 是否为年度完整性所必需。

不同入口发现相同公告时，继续使用规范化官方 URL 和内容指纹去重。来源年度只有在所有必需入口均完成时才可形成完整性结论。

### 4.2 通用发现模式

系统支持以下发现模式：

1. `JCMS_PARAM_JSON`：浙江政务站点的 JCMS 列表与报告总数分页。
2. `STATIC_SUFFIX_TEMPLATE`：通过可配置模板生成 `list2.htm`、`News130a2.htm` 等静态页。
3. `LINKED_PAGE`：根据下一页链接遍历学校或医院列表。
4. `QUERY_PAGE`：通过 `?page=N` 等查询参数分页。
5. `JSON_API`：解析官方 JSON 列表的总页数、总数和详情标识。
6. `EMBEDDED_DATA`：解析官方 HTML 中内嵌的岗位数据对象。
7. `CAMPAIGN_STATE`：只监控当前招聘活动状态，不推断不存在的历史档案。
8. `FIXED_EVIDENCE`：只允许保存仍可访问、且明确标记为证据集而非当前增量入口的页面。

通用发现器必须检测总数突变、重复页、空中间页、末页不一致、超过配置上限和跨主机跳转。任何契约异常都不得静默写成零公告。

### 4.3 传输与安全边界

默认只允许 HTTPS。对于浙江工业大学和国科大杭州高等研究院这类官方站点仅提供 HTTP 的情况，使用显式的 `AUDITED_HTTP_READ_ONLY` 契约：

- 主机和路径前缀必须精确白名单；
- 只允许 `GET` 和 `HEAD`；
- 禁止发送 Cookie、Authorization、账号、表单数据和候选人信息；
- 禁止跟随到非白名单主机；
- 保存响应内容指纹和传输风险标记；
- HTTP 页面只作为公开官方证据，报名和登录仍交给用户浏览器。

附件下载主机逐来源配置。对象存储、招聘子域名或第三方承建系统必须先有官网跳转证据，不能使用全局通配白名单。

### 4.4 内容分类与用工性质

初始招聘和生命周期材料使用不同分类规则。`拟聘、成绩、资格复审、面试、体检、考察、递补、公示` 不得作为新岗位公告，但必须保留为生命周期材料。

岗位导入必须区分：

- 事业编制；
- 员额或备案制；
- 单位正式聘用；
- 国企正式劳动合同；
- 编外或项目聘用；
- 劳务派遣；
- 博士后或纯博士科研岗。

集团、医院多院区和高校附属单位必须保存实际用人主体，不能只记录发布公告的集团或主管单位。

### 4.5 完整性与失败语义

`CONNECTED` 表示当前采集、历史回填和幂等验收均有充分证据；`PARTIAL` 表示采集器正常但官网历史档案或部分必要入口不可证明；`FAILED` 只表示当前已配置来源连续运行失败；`NOT_CONNECTED` 表示尚无可运行采集器。

旧域名失效时，不再把死链接放入可抓取固定证据集。死链接可以作为带状态的历史来源证据保存，但不得导致每天重复抓取失败。

## 6. 已核验来源修复要点

### 6.1 杭州市第一人民医院

移除已 DNS 失效的 `zp.hz-hospital.com` 与 `renshi.wechathospital.com` 页面作为日常抓取目标，保留其历史证据状态。`/dynamic/articles_tag2/id/68` 是“医院新闻”栏目，不得作为招聘入口。

医院官网仍链接的当前招聘系统为 `http://124.160.72.42:8080/apply/index.action`。当前公告与招聘生命周期共用以下链接分页入口：

`http://124.160.72.42:8080/apply/getMore.action?pageNumber=1`

使用 `LINKED_PAGE` 和精确下一页选择器，以第 13 页无下一页作为当前终止证据；第 14 页会重复第 13 页，不能使用“空页终止”。公告详情、附件和当前岗位状态分别限制为 `/apply/getNotice.action`、`/apply/downloadAccessory.action`、`/file_zp/attached/` 与 `/department/detailInfomore.action`。

该系统是非默认端口的明文 HTTP。接入前必须把审计传输契约扩展为精确 authority `124.160.72.42:8080`，只允许 GET/HEAD、上述路径和逐跳重定向复核，不使用 Cookie、登录、表单或 POST。医院官网的 `/recruit/list1`、`/recruit/list2`、`/recruit/articles_tag3/id/98` 仅保留为 2013—2021 的旧档案证据。

2024 年无可访问官方档案，必须保持 `PARTIAL`；2025—2026 只有在 13 页公告、详情、附件和解析计数对账后才可对当前招聘系统形成完整结论，因此来源总体仍为 `PARTIAL`。

### 6.2 杭州市中医院

官方招聘系统使用 `https://hztcm.unitedsoft.cn/News130a{page}.htm`，第一页至第三页可覆盖当前核验到的 2024—2026 档案。招聘和考试通知分别发现，岗位按院区和用工性质保存。

### 6.3 杭州市西溪医院

使用 `https://zp.hzxixih.cn/index/index/announcement.html?page=N` 和独立考试通知栏目。当前核验范围中第一页至第五页覆盖 2024—2026，第六页用于证明越过目标年度。

### 6.4 区县 JCMS

文章正则必须同时接受旧式 `art_<channel>_<id>.html` 和 2026 年 UUID 式 `art_<32hex>.html`。萧山、临平、滨江、余杭和淳安需要多个栏目；不能继续把容器栏目或单一卫生栏目当作全区招聘来源。

## 7. 测试策略

所有生产行为遵循 TDD：先写失败测试并验证预期失败，再实现最小代码。

### 7.1 契约测试

- 多入口去重和角色聚合；
- 必需入口未完成时禁止年度 `COMPLETE`；
- JCMS 报告总数、重复页和末页异常；
- UUID 与旧式文章 URL；
- 静态模板、查询参数、链接分页、JSON API 和内嵌数据；
- 审计型 HTTP 主机、路径、方法和跳转限制；
- 死固定证据不进入日常增量抓取。

### 7.2 解析测试

- 招聘公告与生命周期分类；
- 专业目录工作簿不导入岗位；
- 事业编、正式聘用、国企合同、编外和派遣识别；
- 集团子公司、医院院区和附属单位主体保存；
- 博士后、纯行政和明显不匹配类别排除。

### 7.3 真实验收

每个来源依次执行：

1. 增量运行；
2. 2024—2026 历史运行；
3. 再次增量运行；
4. 核对新增、更新、未变化、失败和下线数；
5. 浏览器检查来源页、年度证据、岗位详情和生命周期信息。

全量完成前运行完整 Maven 测试、前端类型检查和 Vitest，并对生产实例执行健康检查。

## 8. 可观测性与运维

来源页继续展示：

- 当前连接与访问状态；
- 最近成功/失败时间；
- 连续失败次数；
- 年度覆盖和完整性依据；
- 历史不可访问证据；
- 文档与附件问题；
- 生命周期匹配、待关联和歧义计数。

日常调度分散到不同时段，并尊重来源最小请求间隔。历史回填只手动执行或通过受控维护任务执行，不进入每天的增量调度。

## 9. 非目标

- 不自动登录报名系统。
- 不绕过验证码、访问控制或网站明确的反自动化限制。
- 不把第三方招聘汇总网站作为最终资格证据。
- 不因栏目中未发现目标岗位就推断该年度不存在岗位。
- 不在本批次扩展浙江以外地区，也不实现申请跟踪和备考任务管理。

## 10. 交付与版本控制

按三个来源批次分别提交，每批都在私有远程分支 `codex/phase4b-career-workbench` 保留可回滚节点。任何子 Agent 产出必须由主 Agent 检查差异并重新运行测试后才能提交。最终交付包含来源状态矩阵、真实运行编号、年度覆盖、岗位与生命周期计数、未能形成完整性结论的官方原因以及私有仓库提交记录。
