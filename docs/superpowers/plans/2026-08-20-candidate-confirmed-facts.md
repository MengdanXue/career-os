# Candidate Confirmed Facts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make candidate facts server-confirmed, fingerprint-bound inputs so unconfirmed data cannot satisfy eligibility or inflate fit.

**Architecture:** Add a pure domain fact-state model, an application service that coordinates profiles and confirmations through ports, a normalized PostgreSQL adapter, and thin REST/UI adapters. Decision evaluators consume a resolved fact set; profile version changes invalidate current decision snapshots without deleting history.

**Tech Stack:** Java 21, Spring Boot 3.5, PostgreSQL/Flyway/JPA, React 19, TypeScript 7, TanStack Query, JUnit 5, Vitest.

**Spec:** `docs/superpowers/specs/2026-08-20-candidate-confirmed-facts-design.md`

## Global Constraints

- Candidate and decision business rules remain framework-free in `career-domain` and `career-application`.
- Only a current `CONFIRMED` fingerprint may influence a candidate-dependent result positively or deterministically.
- Profile versions are generated by the server on every value or confirmation change.
- Existing decision snapshots remain audit history and are not rewritten.
- PostgreSQL timestamps use `TIMESTAMPTZ`; the confirmation foreign key is indexed by its composite primary key.
