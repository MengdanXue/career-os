# Career OS 产品需求基线

版本：0.1  
状态：从历史需求恢复，作为后续实现的唯一产品基线  
目标窗口：以 2025—2026 历史招聘数据辅助 2027 求职决策

## 1. 产品定位

Career OS 不是通用招聘爬虫，也不是只比较简历与 JD 关键词的 Job Matcher。

它是一个面向杭州、浙江公共数字技术岗位的个人职业决策 Agent：持续采集有证据的招聘信息，判断候选人是否可报，区分编制与用工性质，估计机会重复性和准备成本，并给出可解释的关注、报名与准备建议。

核心问题是：

> 2027 年毕业窗口内，哪些杭州/浙江稳定技术岗位真正可报、值得投入、最可能再次出现，并且适合长期发展？

## 2. 用户目标与约束

### 2.1 已确认画像

- 杭州优先，第一阶段只做浙江、重点杭州。
- 目标是稳定的计算机、软件、数据、AI 应用或信息化专业技术岗位。
- 有多年 Java 后端和企业系统经验。
- 有 AI/GNN 研究经历。
- 有评审取得的“计算机应用中级职称”。
- 出生年月为 1992 年 12 月；精确日期尚未进入项目配置。
- 计划以海外计算机硕士身份参加 2027 招聘；最终毕业日期、留服认证名称和认证完成时间必须在资格判断前确认。

### 2.2 待确认字段

以下字段不得由模型猜测：

- 出生日；
- 硕士最终毕业日期；
- 留服认证后的正式专业名称；
- 留服认证完成日期；
- 政治面貌；
- 报名时劳动合同、社保、档案和“未落实工作单位”状态；
- 户籍、国籍或其他公告特定条件。

字段缺失时，Agent 只能输出“待确认”或条件式结论，不能输出“可报”。

## 3. 目标机会分层

不同用工性质必须分池，不能只给一个“半体制”标签。

### T1：主攻——明确事业编制

- 省、市、区属事业单位计算机/软件/数据/AI/信息化专业技术岗；
- 医院信息中心、数据中心等明确纳入事业编制的岗位；
- 高校、科研院所明确写明“事业编制”或“纳入事业编制”的工程技术岗。

### T2：重点观察——稳定科研/高校技术岗位，但逐岗确认身份

- 新型研发机构、实验室、研究院工程技术岗；
- 高校员额、报备员额、校聘正式岗；
- 公益机构合同制技术岗。

必须明确区分事业编、员额、校聘、项目聘用、合同制和劳务派遣。

### T3：备选——政府背景数字平台和正式国企技术岗

- 杭州市数据集团及其正式技术岗位；
- 市民卡、金投数科、政务云、公共数据平台、数字政府平台；
- 省市属国企的数据平台、Java 后端和 AI 应用岗。

T3 可以是稳定平台，但不得标成事业编。

### 默认排除

- 博士限定科研岗；
- 教师岗；
- 纯行政岗；
- 劳务派遣；
- 短期项目岗；
- 销售岗；
- 无法确认用工性质且公告证据不足的岗位。

排除项应可配置，不能在解析阶段丢失原始岗位。

## 4. 数据范围

### 第一阶段

- 时间：2025-01-01 至 2026-12-31；
- 地区：浙江省，重点杭州；
- 杭州范围：市属、滨江、余杭、钱塘、萧山、临平等；
- 来源：官方公告、岗位附件、官方招聘系统为主，第三方聚合只用于发现和补漏。

2024 数据只在判断连续招聘规律时按需补充，不作为第一阶段全量目标。

### 优先来源

1. 浙江省人社厅及省属单位官方招聘栏目；
2. 杭州市人社局及市属事业单位公告；
3. 杭州各区政府、人社和主管部门栏目；
4. 数据局、发改、经信、科技、卫健等主管部门及下属单位；
5. 高校人事处、信息化部门；
6. 医院官网；
7. 市属、省属国企官方招聘系统；
8. 第三方聚合站，仅作线索源。

## 5. 核心领域模型

系统至少需要以下实体。它们可以在 MVP 中共库实现，不要求一开始拆成八个物理数据库。

### RecruitmentEvent

一次招聘事件：公告、发布单位、发布时间、报名窗口、考试方式、附件和来源证据。

### Job

一个岗位：单位、部门、岗位代码、名称、人数、职责、专业、学历、年龄、应届、经历、政治面貌、职称、社保和其他条件。

### Organization

单位画像：主管部门、单位性质、财政/国资关系、机构层级、所在地、技术生态和证据。

### EmploymentIdentity

用工身份：事业编、员额/报备员额、校聘、国企正式、合同制/编外、劳务派遣、未知。每个结论必须保存公告原文或官方说明证据。

### CandidateProfile

候选人事实、可用资产和待确认信息。资格引擎只能读取已确认事实。

### EligibilityRule / EligibilityAssessment

规则及逐条判定：年龄、学历、学位、专业目录、应届身份、留服、社保/未就业、经历、政治面貌、职称、户籍等。

### CompetitionObservation

已知或估计的招聘人数、开考比例、专业范围宽度、报名人数和考试成本。估计值必须与事实分开。

### OpportunityHistory / Forecast

同一单位或同类岗位跨年度出现记录、连续性、趋势依据和 2027 再现信号。

### Application

发现、资格确认、待报名、已报名、笔试、面试、体检、公示、录用、放弃等状态。

### Evidence

所有关键字段的来源 URL、附件哈希、页/表/行定位、原文片段、采集时间和置信度。

## 6. 决策模型

### 6.1 资格不是分数

资格先做硬判定：

- `ELIGIBLE`：所有硬条件有证据且满足；
- `INELIGIBLE`：至少一项硬条件明确不满足；
- `CONDITIONAL`：满足与否取决于尚未完成的事件，例如留服认证日期；
- `NEEDS_CONFIRMATION`：公告或个人字段不足、专业等同性需招录单位确认；
- `CONFLICTING_EVIDENCE`：不同来源冲突。

只有 `ELIGIBLE` 和经用户确认后的 `CONDITIONAL` 才能进入“建议报名”。

### 6.2 多维评分

通过资格门槛后，分别计算，禁止压成一个不可解释的匹配分：

- `fit_score`：专业、技术、经历和岗位内容匹配；
- `chance_score`：招聘人数、专业限制宽度、考试形式和已知竞争数据；
- `stability_score`：用工身份、单位属性和岗位持续性；
- `growth_score`：技术发挥、职称路线、长期积累和责任边界；
- `future_score`：历史重复、单位持续需求和政策/组织信号；
- `preparation_cost`：笔试、专业测试、材料、时间窗口等成本。

最终只形成策略等级，例如 `MUST_TRACK`、`APPLY`、`VERIFY_FIRST`、`BACKUP`、`REJECT`。任何“上岸概率”都必须标记为估计，并公开依据和不确定性，不能把主观分数伪装成统计概率。

## 7. Agent 与工具边界

### Agent 负责

- 根据用户目标规划需要调用的工具；
- 处理公告中不规则文本和含糊表述；
- 汇总证据、解释结论和提出待确认问题；
- 生成每日变化摘要、岗位分析和准备建议；
- 在规则冲突或证据不足时主动降级结论。

### 确定性工具负责

1. `scan_sources`：发现公告与附件；
2. `download_artifact`：下载并计算哈希；
3. `parse_document`：解析 HTML/XLS/XLSX/DOCX/PDF；
4. `normalize_job`：生成统一岗位模型；
5. `calculate_delta`：新增、变更、下线、未变化；
6. `classify_employment_identity`：基于证据区分用工身份；
7. `evaluate_eligibility`：逐条执行硬规则；
8. `score_opportunity`：输出多维评分；
9. `link_history`：关联跨年度单位和岗位族；
10. `generate_watchlist`：生成分层关注列表。

LLM 不得覆盖硬规则结果，也不得在缺少证据时把“未知”改成“满足”。

## 8. 关键工作流

### 每日增量监控

扫描来源 → 下载新/变更附件 → 解析 → 规范化 → 增量比较 → 资格判定 → 多维评分 → 只推送新增、重要变更、截止临近和下线。

### 历史回填

导入 2025—2026 公告 → 建招聘事件与岗位 → 关联单位和岗位族 → 统计重复出现 → 形成 2027 关注日历。

### 单岗位决策

用户提供 URL/附件/岗位 ID → 提取证据 → 输出用工身份 → 逐条资格结果 → 值得程度 → 风险和待确认问题 → 下一步动作。

### 求职执行（后续阶段）

岗位确认 → 选择事业单位/AI/国企简历版本 → 材料清单 → 笔试/专业面试准备 → Application 状态跟踪。任何投递必须人工确认。

## 9. 人工复核边界

以下情况必须人工复核：

- 公告未明确“事业编制”却需要判断编制；
- 海外专业名称与国内专业目录的等同性；
- 应届、社保、未落实工作单位或档案规则存在地方口径；
- 出生日期不完整且年龄边界可能受影响；
- 官方公告与第三方整理冲突；
- OCR/表格解析置信度不足；
- 岗位涉及政治面貌、职称资格或工作经历的语义组合条件。

人工复核不是失败，而是系统正确处理高风险不确定性的正式状态。

## 10. MVP 验收标准

第一版必须做到：

1. 对至少 10 份代表性官方公告及附件完成可复现解析；
2. 同一批数据重复运行不产生重复新增；
3. 能明确区分事业编、国企正式、合同制、派遣和未知；
4. 能对候选人输出逐条资格判定，不只给关键词匹配分；
5. 缺失个人信息或公告证据时输出待确认，不得猜测；
6. 每个资格结论、用工身份和关键推荐都有可定位证据；
7. 每日结果只报告新增、变更、下线和截止临近；
8. 至少验证一份事业单位岗位表和一份国企招聘附件；
9. 输出 T1/T2/T3 分池榜单，不能混排为“半体制总榜”；
10. 能生成一份 2027 关注清单和资格风险清单。

## 11. 非目标

第一阶段不做：

- 全网无边界爬取；
- 自动投递；
- 绕过登录、验证码或反爬；
- 用 LLM 猜测专业等同性或编制身份；
- 没有历史样本支撑的精确上岸概率；
- Elasticsearch、微服务拆分或复杂多 Agent，仅为技术展示而增加复杂度。

## 12. 实施顺序

1. 固化 CandidateProfile 和待确认字段；
2. 建 Organization / EmploymentIdentity / EligibilityAssessment 契约；
3. 用现有 10 份样本验证用工身份与资格判定；
4. 将现有增量采集接到分层决策流程；
5. 回填 2025—2026 杭州/浙江历史数据；
6. 建跨年度岗位族和 2027 关注日历；
7. 再扩展 Application、简历和面试 Agent。

## 13. Phase 5B Slice 1：个人事实与今日行动

本切片把“数据维护工作台”和“个人每天要处理的事项”分开：

- 首页由后端确定性生成零至三项个人行动，优先级依次为十四天内有效岗位截止、影响目标岗位的资格证据缺口、可证明相关的目标岗位变化；原始 Review Queue 数量不能进入个人行动。
- `CandidateEvidenceTask` 覆盖逐段工作经历、政治面貌、硕士预计毕业月份、海外学历认证、职称、技能及研究材料，并保留站内定位链接。
- `experienceYears` 仅作为旧资料提示。硬资格只能使用已确认、逐段核验的全职日期区间，合并后按完整月份计算；明确确认没有经历时是已知 0 年，未知或部分核验时仍显示未知。
- 决策算法版本会使旧总年数生成的快照失效；有官方报名截止日期时，以该日期作为固定资格参考日，避免进行中经历随查看日期漂移。
- 空技能、空研究关键词和空职称不能通过批量确认变成“明确没有”。V24 只修复已知错误确认，不补写用户未提供的事实。
- API 允许部分数据源不可用时返回 `available=false` 与明确消息，不得用猜测值填补影响数量或截止日期。
