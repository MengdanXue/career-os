# 现有实现与原始需求差距

审计日期：2026-08-14

## 结论

现有工程完成了可靠的数据采集底座，但还不是原始需求中的“杭州/浙江稳定技术岗位职业决策 Agent”。它目前更接近“杭州国企附件增量解析演示”。

## 可以直接保留

| 能力 | 状态 | 处理 |
|---|---|---|
| XLS/XLSX、DOCX、PDF、HTML 解析 | 已实现并测试 | 保留为 Document Tools |
| 来源 URL、附件哈希、行/页定位 | 已实现 | 保留并扩展到所有决策证据 |
| 稳定岗位键、内容指纹 | 已实现 | 保留 |
| 新增/变更/下线/未变化 | 已实现 | 保留，接入每日摘要 |
| Spring AI `@Tool` 注册 | 已实现 | 保留框架，重做领域工具 |
| 无模型密钥的确定性回退 | 已实现 | 保留 |

## 必须重构

| 当前实现 | 问题 | 目标 |
|---|---|---|
| `scan_official_recruitment_sources` 只扫 S09/S10 国企源 | 偏离“事业编优先” | 首先覆盖省/市事业单位和官方附件，国企单独作为 T3 |
| `find_it_job_candidates` | 只有通用 IT 关键词相关度 | 替换为用工身份、资格判定和多维机会评估 |
| `classification.score` | 容易被误解为最终匹配分 | 仅保留为文本分类置信度，不进入最终决策 |
| 每日工作流固定导入最新 S09 附件 | 来源、附件和事件写死 | 按 source adapter 和 RecruitmentEvent 编排 |
| `employer.organization_type` | 粒度不足 | 增加主管部门、事业单位类别、国资关系和证据 |
| `position.employment_type` | 枚举有基础但没有判定证据 | 建 EmploymentIdentity 结论、依据、置信度与复核状态 |

## 尚未实现的核心能力

1. CandidateProfile 及字段确认状态；
2. 留服、专业目录、应届、社保、年龄等资格规则；
3. `ELIGIBLE / INELIGIBLE / CONDITIONAL / NEEDS_CONFIRMATION` 结果；
4. 事业编 T1、待确认稳定岗位 T2、国企 T3 分池；
5. Organization 和 RecruitmentEvent 持久模型；
6. 跨年度岗位族、重复招聘和 2027 关注信号；
7. 竞争、稳定、成长、准备成本等多维评分；
8. PostgreSQL 持久化与可审计决策记录；
9. 关注清单、截止提醒和求职状态跟踪；
10. 事业单位、AI、国企三类材料和面试准备工作流。

## 优先改造路线

### P0：先让结论正确

- 固化候选人事实与未知字段；
- 增加 EmploymentIdentity 和 EligibilityAssessment；
- 对现有样本做“编制/派遣/国企 + 是否可报”验收；
- Agent 遇到未知信息时必须停止在 `NEEDS_CONFIRMATION`。

### P1：再让数据覆盖目标市场

- 接入浙江省人社、杭州市人社及代表性高校/医院来源；
- 按 2025—2026 回填；
- 建单位与岗位族历史关联。

### P2：最后做策略与执行

- 多维评分和 T1/T2/T3 关注清单；
- 2027 月度关注日历；
- 材料、笔试、专业面和 Application 跟踪。

## 当前样本的正确用途

- S01—S08：用于验证事业单位、高校、医院公告及附件解析和资格字段；
- S09—S10：用于验证国企来源、正式招聘系统、空状态和增量更新；
- 不能用 S09 的 101 个岗位代表整个杭州半体制机会池；
- 不能用“IT 关键词命中数”替代是否可报或是否值得投。
